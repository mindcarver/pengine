# L4 实际实现设计

> 状态：已实现。本文以当前 `main` 的代码、测试和已提交人格资产为权威依据，对应
> [Issue #109](https://github.com/mindcarver/pengine/issues/109) 与
> [PR #111](https://github.com/mindcarver/pengine/pull/111)。

L4 是创作者已确认的价值观与短剧技艺合同。它一方面指导各生成阶段，另一方面为独立 Reviewer 和最终 L4 Gate 提供可引用的硬规则。本次不设计 L5/L6。

## 1. 三种权限必须分开

| 类型 | 当前所有者 | 运行效力 |
| --- | --- | --- |
| L4-A / L4-B 中明确标为“硬规则”的条款 | 创作者确认 | 可成为生成约束、阶段 Reviewer blocker 和最终 L4 Gate 证据 |
| “已确认创作建议” | 创作者确认 | 只指导生成，不能单独阻断 |
| 集数、单集时长、场数默认值 | Pengine | 产品参数；用户明确要求或锁定参数优先 |

长剧体量、题材偏好、市场转译、未确认的 AI 推导和“像不像某创作者”都不是 L4 硬 Gate。

## 2. 运行因果链

```text
personas/<persona>/l4.md
  → manifest/hash/schema/必需标题校验
  → 不可变 persona snapshot
  → PersonaCatalog._stage_l4_context()
  → 生成阶段的 L4-A + 通则 + 当前阶段 + Pengine 参数
  → Worker 按 /persona/l4/<stage>.md 命名投影
  → 专业 Agent 生成 / 独立 Reviewer 出具硬规则证据
  → quality_reviewer 读取完整 L4 做 accepting_l4
  → Worker 验证证据标签
  → DeliveryReport.l4_gate + 人格快照身份持久化
```

L4 并不直接把候选写入已批准 checkpoint。模型输出必须继续通过结构、Canon、StoryContract、SeriesBible、SeriesState、前缀绑定和持久化事务。

## 3. 资产合同与快照

`src/pengine/personas.py` 要求 `l4.md` 至少包含：

- `L4-A` 价值观；
- `L4-B` 短剧技艺；
- 故事大纲、人物小传、人物关系、分集大纲、分集剧本；
- 参数段。

文件作为 persona 固定集合的一部分参与 `package_sha256` 和 `snapshot_sha256`。快照只保存已授权编译后的 `l4.md` 与来源指纹，不把原始 L9 研究资料、访谈或未确认推导放入 prompt、SQLite 或观测系统。

旧任务继续使用创建时的 snapshot。修改 L4 必须更新文件 hash、包 hash 和 persona 版本，只影响新任务。

## 4. 阶段投影矩阵

`_stage_l4_context()` 的当前行为如下：

| 内部阶段 | `/persona/l4/<stage>.md` 内容 |
| --- | --- |
| `selecting_l0_variant` | 仅 L4-A |
| `generating_story_outline` | L4-A + 全阶段通则 + 故事大纲 + Pengine 参数 |
| `generating_character_relationships` | L4-A + 全阶段通则 + 人物小传 + 人物关系 + Pengine 参数 |
| `generating_episode_outline` | L4-A + 全阶段通则 + 分集大纲 + Pengine 参数 |
| `generating_episode_scripts` | L4-A + 全阶段通则 + 分集剧本 + Pengine 参数 |
| `accepting_l0` | 仅 L4-A；L0 Gate 仍只验收 L0 |
| `accepting_l4` | 完整 `l4.md` |

`loading_persona` 和 `assembling_delivery` 不是专业 Agent 阶段，`Worker._persona_files()` 不为它们创建 L4 工作文件。

还需要明确一个真实的实现边界：Worker 会预先把七个专业阶段的投影以不同路径放进同一 Deep Agents 只读 VFS。阶段投影防止各文件自身混入无关规则，当前 Agent 通过 prompt 约定只读当前 `/persona/l4/<stage>.md`；这不是按子 Agent 建立的文件系统 ACL。

## 5. 生成、修复与审核

`src/pengine/agents.py` 的 `_L4_POLICY` 被加入 story architect、episode planner、script writer、story/episode repair、canon/episode/series reviewer 和 quality reviewer 的 system prompt。

### 生成阶段

专业生成 Agent 读当前阶段投影，并同时服从用户要求、已批准 checkpoint、Canon、L0、StoryContract 和生产参数。已确认创作建议可以影响表达选择，但不能伪装成锁定事实或 blocker。

### 修复路径

- `story_repair` 和 `episode_repair` 是专业子 Agent，可读取阶段化 L4 文件，但只能修复 Reviewer 已确认的问题；
- Story/Outline 直接补丁调用不运行 Deep Agent VFS，当前不直接内联 L4 阶段正文；它们只执行独立 Reviewer 已绑定的最小补丁范围，并在补丁后重新进入审核；
- 任何修复都不能以 L4 为由改写已锁上游。

### 阶段 Reviewer

Canon 和 Series Reviewer 的通过证据必须包含精确标签 `L4硬规则：`，并说明检查了哪些当前适用的创作者确认硬规则。`_require_l4_stage_evidence()` 和 Worker checkpoint 验证会拒绝缺少该标签的“通过”结果。

在统一 SeriesBible 流程中，每集先执行确定性合同/状态校验；系列级 Reviewer 只在声明的结构里程碑与最终前缀运行。不应把旧兼容路径中的 `episode_reviewer` 误写成当前统一流程的每集必调模型。

### 最终 L4 Gate

`quality_reviewer` 在 `accepting_l4` 读取完整 `/persona/l4/accepting_l4.md`，把 L0 作为只读上下文，不重选或重开 L0。通过证据必须同时包含：

- `L4-A：`；
- `短剧硬规则：`；
- `产品参数：`，且必须写明所有者是 Pengine，并说明是否被用户要求或锁定参数覆盖。

Worker 对这三个标签做确定性验证。不通过时进入 `quality_rejected`，保留已批准内容和证据；`retry-final-review` 只重跑最终 Gate，不重生前面内容。

## 6. 存储边界

L4 的持久化证据分三层：

1. creation 绑定 `persona_id`、版本和 `persona_snapshot_sha256`，因此可回溯精确 L4 资产；
2. 故事/人物/合同/系列审核证据随业务 checkpoint 或绑定 review 记录保存；
3. 最终 `DeliveryReport.l4_gate` 保存通过证据。

`DeliveryReport` 不复制 L4 全文，也不把 Pengine 默认参数改写为创作者规则。正式交付还必须绑定当前 SeriesBible、script batch、active prefix 和通过的最终全剧 review。

## 7. 代码责任映射

| 路径 | 当前责任 |
| --- | --- |
| `contracts/persona-package.schema.json` | v3 包结构和 `l4.md` hash 合同 |
| `src/pengine/personas.py` | L4 必需标题、快照、阶段投影和上下文上限 |
| `src/pengine/worker.py` | 阶段投影命名、checkpoint 证据标签验证、Gate 恢复与交付组装 |
| `src/pengine/agents.py` | 硬规则/建议/参数权限，生成、修复、Reviewer 和最终 Gate prompt |
| `src/pengine/schemas.py` | `GateResult`、`DeliveryReport.l4_gate` 和对外交付合同 |
| `src/pengine/repository.py` | 业务 checkpoint、拒绝证据、系列 review 与最终交付事务 |
| `personas/shouzhuo/l4.md` | 已确认的守拙 L4 运行资产 |

## 8. 验收方法

确定性回归：

```bash
uv run pytest tests/test_personas.py tests/test_agents.py tests/test_worker.py \
  tests/test_repository.py tests/test_unified_integration.py -q
```

关键证据包括：

- 四个生成阶段各自只在当前投影文件中得到通则、本阶段规则和参数；
- 创作建议不阻断，Pengine 参数不被归因为创作者规则；
- 通过的阶段 Reviewer 必须给出 `L4硬规则：` 证据；
- 通过的最终 Gate 必须给出三组权限标签；
- 旧 snapshot 不被新 L4 覆盖，正式交付绑定通过 Gate 和当前剧本 lineage。

真实模型 A/B/C 是显式 opt-in：

```bash
PENGINE_RUN_L4_ABC=1 uv run pytest -m live_model \
  tests/live/test_l4_persona_e2e.py -vv -s
```

它用来检查基线、硬规则和创作建议三组运行差异，但真实模型样本不能代替确定性投影、证据标签、快照和交付事务验证。
