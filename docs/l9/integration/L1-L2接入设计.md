# L1 + L2 合并为 Soul 的接入设计

## 0. 最终结论

L1 与 L2 不再作为两个运行时人格分面分别注入。两份原始资料继续分开保存和审计，其中经真人确认、稳定、能转译为创作行为的内容，离线编译成一个 `soul.md`。

`soul.md` 是 L1 + L2 的唯一运行时人格真源。所有模型阶段读取同一份完整 Soul，不抽取 `## 摘要`，不在运行时重新总结，不按检索结果拼装，也不允许静默截断。

```text
L1 原始资料 ─┐
             ├─> 人工校准、去重、降权、确认
L2 原始资料 ─┘
                     └─> personas/<creator>/soul.md
                               └─> manifest + immutable snapshot
                                         └─> /persona/soul.md 全文只读挂载
                                                   └─> 所有模型阶段完整读取
```

第一版明确排除：

- 精确出生日期、时间、地点和其他可识别个人资料。
- 四柱、十神、神煞、星座、宫位、相位等推演过程。
- 大运、流年、行运以及 2026—2040 等时间性预测。
- 财富、关系、事业、合作、项目成败和人生安排建议。
- “两套系统撞上，所以是铁结论”之类确定性声明。
- Soul Gate、Soul Reviewer、Soul Memory、Soul Skill、Soul RAG 或独立数据库表。

Soul 的权限是：**稳定的创作身份、观察方式和表达默认值**。它不是现实人格诊断，不是剧情事实，不是故事模板，也不是质量硬闸。

运行时优先级保持为：

```text
用户明确需求 / 已批准 checkpoint / 已锁定 Canon
  > L0 母题与雷区
  > L4 手艺标准与参数
  > L3 创作方法
  > Soul 创作身份与表达默认值
```

## 1. 架构决策

### 1.1 场景与目标

Pengine 是固定工作流与动态创作 Agent 结合的 `workflow_agent_hybrid`。主流程、checkpoint、snapshot、Canon 和 Gate 由 Workflow 控制；故事、人物、分集与剧本表达由 Agent 动态完成。

本设计只解决一个问题：

> 怎样把 L1 与 L2 中有创作价值的稳定内容，变成所有创作 Agent 都能一致读取、可复现、可审计、不会越权的创作人格。

Agent Fit 已由现有剧本工作流确定，不在本设计中重新评估。风险等级为 `medium`：Soul 只读、不触发外部动作，但会长期影响模型生成，如果边界错误会造成角色同质化、母题固化、隐私扩散或审核偏置。

目标方案类型：

```text
workflow_agent_hybrid
  + immutable persona snapshot
  + one authoritative Soul
  + existing L0/L4 reviewers
```

自主级别为 `assistive`：Agent 可以根据 Soul 调整创作观察与表达，但不得据此改写用户要求、Canon、工作流状态、预算、排期、Gate 或现实决策。

### 1.2 当前实现与目标实现

当前 persona v1 的真实行为是：

- 包协议固定要求 `l1.md` 与 `l2.md`。
- `_project_stage_context()` 分别抽取两份文件的 `## 摘要`。
- 运行时分别挂载 `/persona/l1-summary.md` 和 `/persona/l2-summary.md`。
- `project.md` 还可能重复写 L1、L2 摘要，形成多个可漂移来源。

目标 persona v2 改成：

- `soul.md` 替代运行包中的 `l1.md` 与 `l2.md`。
- `/persona/soul.md` 是唯一人格入口。
- `soul.md` 全文进入所有模型阶段。
- `project.md` 只保留 Soul 的状态、权限和指向，不复制正文。
- 新任务绑定 v2 snapshot；历史 v1 snapshot 保持旧投影，不在恢复时自动改 Prompt。

### 1.3 为什么 L1 与 L2 应在运行层合并

原始 L1、L2 按“推演体系”分开，但对剧本 Agent 而言都在回答同一个运行问题：

> 这个创作人格通常如何感受、观察、选择张力并形成表达？

继续分成两个摘要会产生三个问题：

1. **重复加权**：两份材料都出现“理念驱动、有人文温度、理想与现实张力、与常规摩擦”等描述，模型可能把近义表达当成多条独立指令。
2. **层间冲突**：L1 的表达倾向与 L2 的能量倾向没有统一仲裁，发生冲突时只能由模型临场猜测。
3. **真源漂移**：`project.md`、`l1.md`、`l2.md` 可能各写一版摘要，更新时容易不一致。

Soul 通过一次离线编译完成去重和仲裁，运行时只保留一个权威人格。

### 1.4 “交叉验证”的证据边界

L1 与 L2 使用同一对象的出生资料；L2 后半部分还显式引入 L1，写有“L1×L2 双系统交叉”和“撞上=铁结论”。因此现有文本不是两份相互盲化的独立证据。

设计中统一使用以下状态：

| 状态 | 含义 | 是否可进入 Soul |
| --- | --- | --- |
| 单一来源候选 | 只在 L1 或 L2 中出现 | 真人确认后可以 |
| 跨来源趋同 | 两边有近义描述，但不代表独立验证 | 真人确认并去重后可以 |
| 推演判断 | 由术数规则推得、没有创作行为证据 | 不直接进入 |
| 现实反馈确认 | 真人认为长期稳定且能转成创作动作 | 可以 |
| 时间性预测 | 只对某个年份或阶段生效 | 不进入稳定 Soul |

任何条目都不能因为“L1、L2 都这样说”自动升级为事实。

### 1.5 候选方案比较

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 保持 v1，分别注入 L1/L2 摘要 | 不采用 | 重复、冲突、真源分散，不能形成统一人格 |
| 合并两份原始全文并直接注入 | 不采用 | 包含隐私、推演术语、时间预测和现实建议，权限和上下文成本过大 |
| 每次调用由模型临时总结 L1/L2 | 不采用 | 不可复现，不同阶段可能得到不同人格，难以审计 |
| 用 RAG 按任务检索 L1/L2 | 不采用 | 身份不应依赖召回命中；不同调用会看到不同人格切片 |
| 把 L1/L2 写入 Memory 或 Skill | 不采用 | 它既不是会话事实，也不是操作流程；自动生长会污染稳定人格 |
| 离线编译一个 Soul，运行时全文读取 | **采用** | 单一真源、可审计、可冻结、可控制权限，符合稳定身份的职责 |

### 1.6 与 Hermes / OpenClaw 的类比边界

本设计借鉴的是人格分层，不照搬通用助手的目录结构：

- Hermes 把 `SOUL.md` 定义为稳定身份、语气、交流默认值，并与项目工作规则分开；内容作为身份直接进入系统提示词。参见 [Hermes SOUL.md 官方说明](https://hermes-agent.nousresearch.com/docs/guides/use-soul-with-hermes)。
- OpenClaw 也把 `SOUL.md`、`AGENTS.md`、`USER.md`、`MEMORY.md` 与工作日志分开。参见 [OpenClaw Agent Workspace](https://docs.openclaw.ai/concepts/agent-workspace)。

Pengine 的对应关系是：

| 通用 Agent 概念 | Pengine 对应物 | 边界 |
| --- | --- | --- |
| Soul / Persona | `soul.md` | 稳定创作身份、观察与表达默认值 |
| Constitution | `l0.md` | 最高母题、雷区和温度，优先于 Soul |
| Project instructions | `project.md`、`l3.md`、`l4.md`、阶段 Prompt | 工作流、方法、标准和仲裁 |
| Memory | checkpoint、Canon、反馈和运行状态 | 已发生事实与持久状态，不保存 Soul |
| Skills | `agent_skills/` | 可执行创作技法，不保存人格判断 |
| Temporary personality | 未来可选 overlay | 临时模式，不修改稳定 Soul |

## 2. Soul 内容编译契约

### 2.1 来源分级

原始 L1、L2 先按用途拆分，再决定是否进入 Soul：

| 类型 | 原始内容示例 | 处理 |
| --- | --- | --- |
| A. 个人资料与盘面 | 出生信息、四柱、十神、行星、宫位、相位 | 只留在受控来源，不进入运行包 |
| B. 稳定创作身份 | 为理念而写、重视人文温度、表达具有作者信念 | 真人确认后进入 `身份` |
| C. 观察与表达 | 关注具体细节、关系温度、行动与代价、意在言外 | 真人确认后进入 `观察与表达` |
| D. 创作能量 | 深掘、强表达、敢于突破常规、将想法落实为作品 | 转译成创作默认行为后进入 |
| E. 生产性张力 | 理想与现实、信念与规则、温柔与坚硬 | 可作为观察镜头，不得自动升级为每部作品的母题 |
| F. 现实人格与合作建议 | 固执、易受伤、需要某类搭档 | 不作为 Agent 对真人的判断；只有可转译的创作行为才可能进入 |
| G. 时间性内容 | 大运、流年、行运、具体年份建议 | 第一版不接入 |

### 2.2 从现有 L1/L2 到 Soul 的转译规则

| L1/L2 候选结论 | 不能直接写成 | Soul 中可使用的创作表达 |
| --- | --- | --- |
| 思想即作品、为理念而写 | “创作者天生肩负使命” | 作品倾向让价值立场通过人物选择、制度压力和后果显形 |
| 有温度、能打动人 | “创作者一定温柔、共情力强” | 冲突前先建立可见的照料、依赖和日常暖意，让失去有重量 |
| 理想与现实是深层张力 | “所有作品必须写理想破灭” | 可优先观察信念遇到现实压力时人物如何选择，但本剧母题仍由 L0 决定 |
| 创作深而烈 | “必须黑暗、痛苦、极端” | 关键情感不轻轻带过，要追到人物选择、代价和关系后果 |
| 不肯随流、与规则摩擦 | “平台和规则都是敌人” | 可寻找人物与既定秩序的真实摩擦，但不能破坏 L4、Canon 或项目规则 |
| 知行合一、行动力强 | “创作者本人一定能成事” | 场景优先用行动推进信念，不用抽象宣言代替戏剧行为 |
| 关系里容易理想化 | “创作者会在合作里受伤” | 不进入现实判断；只有本剧需要时，作为人物关系的可选观察镜头 |

### 2.3 `soul.md` 文件职责

`personas/<creator>/soul.md` 是一份短而完整的创作人格正文，不再设置“来源画像全文 + 运行摘要”两层，也不要求 `## 摘要`。

必须包含：

1. 身份：这个创作人格在作品中持续追求什么。
2. 观察与表达：更自然地看见什么、如何把它写成戏。
3. 创作能量：默认节奏、深度、行动倾向和表达力度。
4. 生产性张力：擅长处理哪些矛盾，但不得把它们固定为所有作品的主题。
5. 避免：最容易过度使用或造成同质化的表达。
6. 权限与仲裁：Soul 必须让位于用户、Canon、L0、L4、L3 和 checkpoint。
7. 来源状态：L1/L2 指纹、真人确认状态和非事实声明。

禁止包含：

- 精确出生资料或可识别个人信息。
- 术数推演步骤和要求模型相信推演正确的指令。
- 具体年份、年龄、事业、财富、健康、关系或合作预测。
- 未确认却写成确定事实的人格断语。
- 工具、路径、命令、工作流、模型路由和 Gate 规则。
- 与 `project.md`、`l0.md`、`l3.md` 或 `l4.md` 重复的正文。

### 2.4 建议模板

```markdown
# <人格名> Soul

> 来源：由 L1 与 L2 的稳定创作部分人工编译；不是现实人格诊断或命运预测。
>
> L1 指纹：sha256:<hash>
>
> L2 指纹：sha256:<hash>
>
> 状态：创作者已确认 / AI 草稿待确认 · 归属：<归属方>

## 身份

<这个创作人格持续追求的作品意义与作者姿态。>

## 观察与表达

- <稳定观察镜头。>
- <稳定表达方式。>

## 创作能量

- <节奏、深度、行动和表达力度的默认值。>

## 生产性张力

- <擅长观察的矛盾。>
- 这些张力只是创作镜头；是否成为本剧母题由 L0 决定。

## 避免

- <容易造成千剧一面、角色同质化或过度表达的模式。>

## 权限与仲裁

- Soul 只影响观察、细节、人物压力、行动、节奏和对白质感。
- Soul 不得新增故事事实，不得覆盖用户要求、Canon、checkpoint、L0、L4、L3 或 StoryContract。
- Reviewer 不得以“不像 Soul”为由拒绝作品。
```

### 2.5 全文读取与大小边界

“全文读取”在本设计中有严格含义：

- 运行时读取 snapshot 中 `soul.md` 的全部 UTF-8 文本。
- 不抽取某个 Markdown 标题。
- 不做模型摘要、RAG 召回或阶段切片。
- 不在超限时截掉尾部继续运行。
- 每个模型阶段读取相同字节内容和相同 Soul hash。

第一版把 `soul.md` 上限定为 **8,000 个 Unicode 字符**。超过上限时 persona 校验失败，由人缩短并发布新版本；不能用静默截断破坏“全文读取”的承诺。该上限是首版工程预算，需要通过真实模型验收复核，不代表 8,000 字符一定是质量最优点。

## 3. Persona v2 包协议

### 3.1 文件集合

persona v1 当前包含九个 Markdown 文件：

```text
paradigm.md
project.md
l0.md
l1.md
l2.md
l3.md
l4.md
l5.md
l6.md
```

persona v2 由 `soul.md` 替代运行时 `l1.md + l2.md`：

```text
paradigm.md
project.md
l0.md
soul.md
l3.md
l4.md
l5.md
l6.md
```

原始 L1/L2 继续保存在受控来源区，通过 `soul.md` 顶部的来源指纹追踪，不复制进 persona 包。

### 3.2 Manifest 与 package hash

persona v2 的 manifest 使用 `schema_version: "2.0.0"`：

- `files` 必须包含 `paradigm`、`project`、`l0`、`soul`、`l3`、`l4`、`l5`、`l6`。
- v2 包不得再包含 `l1.md` 或 `l2.md`，避免出现双真源。
- `package_sha256` 按上述八个逻辑文件的固定顺序计算。
- `soul.md` 的 SHA-256 进入 manifest，并随 persona snapshot 冻结。
- 原始 L1/L2 指纹写在 Soul 正文中，因此也间接进入 `soul.md` 和 package hash。

不在 manifest 增加完整原文路径，避免把本地目录或敏感资料位置扩散到 snapshot。

### 3.3 v1 历史快照兼容

兼容的目的不是让新旧格式长期混用，而是保证已经创建的任务可以按原 Prompt 恢复。

规则：

- v1 source package 只允许用于解析已有 snapshot，不再创建新的生产任务。
- v1 snapshot 恢复时继续挂载原有 `/persona/l1-summary.md` 与 `/persona/l2-summary.md`，不临时合成 Soul。
- v2 snapshot 只挂载 `/persona/soul.md`，不暴露 L1/L2 摘要路径。
- 运行中任务不得从 v1 自动升级到 v2。
- 新任务只使用迁移完成的 v2 persona。
- 不允许一个 package 同时存在 `soul.md`、`l1.md` 和 `l2.md`。

这样既保留历史可复现性，也避免新架构继续承受双路径。

### 3.4 `project.md` 的职责调整

v2 `project.md` 不再保存 L1、L2 摘要，只保留状态和权限指向：

```markdown
## Soul 状态

- [创作者已确认][归属：<归属方>] 创作人格正文读取 `/persona/soul.md`。
- Soul 是软性创作身份，不得覆盖用户要求、Canon、L0、L4、L3、StoryContract 或 Gate。
```

同一条人格内容只允许出现在 `soul.md`，不能在 `project.md` 再写一份近义版本。

## 4. 组件设计与职责边界

| Component | Responsibility | Input | Output | Owner |
| --- | --- | --- | --- | --- |
| Source curator | 从 L1/L2 中分离稳定内容、敏感内容和时间内容 | 两份原始资料 | Soul 候选条目与来源映射 | Human |
| Human approver | 确认哪些条目代表稳定创作人格 | 候选条目 | 已批准 Soul 正文 | Creator / authorized owner |
| Persona validator | 按 schema version 校验文件集合、标题、状态、大小和 hash | persona package | valid package 或明确错误 | Workflow |
| Snapshot builder | 冻结完整 persona 内容与 manifest | valid package | immutable snapshot | Workflow |
| Context projector | v2 全文挂载 Soul；v1 维持历史投影 | snapshot + stage | read-only `/persona` context | Workflow |
| Creative Agent | 使用 Soul 调整观察、表达、节奏和人物压力 | brief + workspace + persona | 创作候选 | Agent |
| L0/L4 Reviewer | 只按自身契约审核，Soul 仅作背景 | candidate + L0/L4 + Canon | gate decision + evidence | Reviewer |
| Policy guard | 阻止 Soul 越权、敏感资料进入运行包和混合格式 | package + prompt contract | allow / reject | Workflow |
| Evaluator | 比较 Soul 开启与中性 Soul 的行为差异 | isolated runs | evaluation report | Human + Eval workflow |
| Logger / tracer | 记录版本、hash、字符数和挂载路径，不记录原始敏感来源 | runtime metadata | trace / audit evidence | Workflow |

### 4.1 Agent 应该做什么

- 读取完整 `/persona/soul.md`。
- 在不改变事实和质量标准的前提下，让作品体现约定的观察与表达倾向。
- 让不同人物从各自传记、处境和关系出发，而不是复制创作者人格。
- Soul 与更高优先级约束冲突时明确让位。

### 4.2 Agent 不应该做什么

- 解释、验证或重新计算八字和星盘。
- 从 Soul 推断创作者现实经历、健康、财富、关系或未来。
- 把 Soul 变成每个角色的人格模板。
- 根据 Soul 修改集数、预算、排期、模型路由或工作流状态。
- 因为某段“不像 Soul”而拒绝候选。

### 4.3 Workflow、Tool、RAG、Memory 与 Human 边界

- **Workflow**：负责 schema、版本、hash、snapshot、挂载、优先级、错误和审计。
- **Tool**：本设计不新增工具；读取 `/persona/soul.md` 继续使用现有只读 workspace 能力。
- **RAG**：不参与运行时人格装配；原始 L1/L2 不做动态检索。
- **Memory**：不保存或自动更新 Soul；任务反馈不能直接改写人格。
- **Human**：负责来源授权、内容确认、冲突仲裁和新 persona 版本发布。
- **Reviewer**：L0/L4 继续作为硬 Gate；第一版不新增 Soul Reviewer。

## 5. 控制流、数据流与状态

### 5.1 Authoring Control Flow

```text
读取受控 L1/L2
  -> 分类：敏感资料 / 稳定人格 / 创作行为 / 时间预测 / 现实建议
  -> 合并近义项并标注来源
  -> 把人格断语转成可观察的创作行为
  -> 真人逐条确认
  -> 写入 soul.md
  -> persona v2 schema + hash + size 校验
  -> 更新 persona version
  -> 创建 immutable snapshot
  -> 只让新任务选择该版本
```

### 5.2 Runtime Data Flow

```text
Task binds snapshot_sha256
  -> PersonaCatalog resolves exact snapshot
  -> schema_version == 2.0.0
  -> validate soul.md hash and <= 8,000 chars
  -> mount exact full text as /persona/soul.md
  -> provide same full text to every model stage
  -> Agent generates candidate
  -> Canon / L0 / L4 reviewers evaluate by their own contracts
  -> trace records persona version + snapshot hash + soul hash + char count
```

### 5.3 状态转换

| 当前状态 | 触发 | 下一状态 | Owner |
| --- | --- | --- | --- |
| `sources_received` | 来源和授权已确认 | `soul_drafting` | Human |
| `soul_drafting` | 完成去重与转译 | `awaiting_human_confirmation` | Human |
| `awaiting_human_confirmation` | 真人逐条确认 | `soul_confirmed` | Human approver |
| `soul_confirmed` | schema/hash/size 通过 | `package_valid` | Workflow |
| `package_valid` | 创建 snapshot | `snapshot_ready` | Workflow |
| `snapshot_ready` | 新任务选择 persona | `snapshot_bound` | Workflow |
| `snapshot_bound` | 阶段模型调用 | `soul_mounted` | Context projector |
| `soul_mounted` | 模型完成输出 | `candidate_created` | Agent |

未确认条目不得进入 `soul_confirmed`。不能通过“AI 自己认为合理”跳过真人确认。

### 5.4 Tool、RAG 与审批流

本设计没有新增 Tool Call 或 RAG Flow。唯一读取动作是从已绑定 snapshot 读取已校验的 `soul.md`，权限为只读。

Human Approval 发生在 persona 发布之前：

```text
AI/人工编译草稿
  -> 展示条目、来源、转译和排除理由
  -> 真人确认 / 修改 / 否定
  -> 只有确认版本可以计算新 package hash
```

### 5.5 错误处理

| 错误 | 行为 |
| --- | --- |
| v2 缺少 `soul.md` | package validation fail closed |
| v2 同时含 `l1.md`/`l2.md` | `mixed_persona_schema`，拒绝加载 |
| Soul 超过 8,000 字符 | `soul_too_large`，拒绝加载，不截断 |
| Soul hash 与 manifest 不一致 | `persona_hash_mismatch`，拒绝加载 |
| Soul 含待确认标记 | package validation fail closed |
| v1 历史 snapshot | 使用 v1 固定投影，不自动升级 |
| snapshot 缺失或损坏 | 沿用现有 persona snapshot 错误，不回退到当前 source package |
| Soul 与 L0/L4 冲突 | 运行时服从 L0/L4，并记录可观测冲突证据 |

## 6. 全阶段使用规则

所有模型阶段都全文读取同一个 Soul，但“读取全文”不代表 Soul 在所有阶段拥有相同权限。

| 阶段 | 允许使用 | 明确禁止 |
| --- | --- | --- |
| L0 侧面确认 | 理解创作身份的背景 | 根据 Soul 自动新增、替换或优先选择 L0 侧面 |
| 故事大纲 | 选择观察角度、冲突质感和人物行动方式 | 新增命定事件、创作者传记或时间预测 |
| 人物与关系 | 建立具体温度、信念、行动与代价 | 把全部人物写成同一种性格 |
| 分集大纲 | 安排压力升级、节奏和选择落点 | 覆盖 L4 参数、集数和 StoryContract |
| 分集剧本 | 影响动作、物件、潜台词和表达力度 | 在正文中解释命理、星盘或人格结论 |
| Canon / 连续性审核 | 读取但不把 Soul 当事实 | 把“不像 Soul”判成连续性错误 |
| L0 Gate | 读取但只按 L0 契约审核 | 引用 Soul 作为通过或拒绝证据 |
| L4 Gate | 读取但只按 L4 契约审核 | 把 Soul 偏好升级为手艺标准 |
| 最终审核 | 可检查是否发生 Soul 越权 | 以人格贴合度替代故事质量和交付要求 |

### 6.1 防止角色同质化

Soul 描述的是创作者镜头，不是角色模板：

- 人物首先服从 biography、relations、StoryContract、Canon 和已写前缀。
- Soul 可以影响“镜头更容易看见什么”，不能决定“人物一定是什么人”。
- 对照人物、反派和配角必须从各自处境生长，不能只是 Soul 的正反例。
- 真实模型验收必须检查不同角色的价值观、语言、行动策略和关系位置是否仍有区分。

### 6.2 防止 Soul 成为第二个 L0

```text
L0：本剧最终要守住、追问和拒绝什么
Soul：这个创作人格通常怎样感受、观察和表达
L3：创作过程怎样思考、拆解和推进
L4：作品必须达到哪些可验收标准
```

即使 Soul 与 L0 出现相同词语，也只能由 L0 决定本剧母题。Soul 不得通过重复强调提高自身权限。

## 7. 风险边界与护栏

### 7.1 风险边界

| 边界 | 允许 | 禁止 |
| --- | --- | --- |
| Data | 经确认的创作倾向和来源 hash | 精确出生资料、现实隐私和完整推演过程 |
| Action | 只影响创作候选 | 外部发送、发布、付款、排期、合作或人生决策 |
| Memory | snapshot 冻结版本 | 根据普通任务反馈自动改人格 |
| Output | 创作表达与非阻断性观察 | 现实人格诊断、命运预测和确定性标签 |
| Review | 检查是否越权和是否服从 L0/L4 | 以 Soul 匹配度作为硬 Gate |
| Cost | 全文读取受 8,000 字符上限控制 | 超限后静默截断、自动摘要或隐式增费 |

### 7.2 必需护栏

- Persona schema 与文件集合按版本严格校验。
- `soul.md` 字符上限、UTF-8、hash、确认状态和只读挂载校验。
- v2 禁止 L1/L2 与 Soul 混合存在。
- Source PII 不复制到 persona、snapshot、日志、Langfuse 或交付包。
- Prompt 明确 Soul 的 advisory 权限和仲裁顺序。
- Reviewer 提示词明确禁止把 Soul 当 Gate 标准。
- Trace 只记录 schema version、persona version、snapshot hash、soul hash、字符数和挂载结果。
- 发现证据冲突时降级为“待确认”，不得由模型自行选择更讨喜的版本。
- 运行时不访问原始 L1/L2，从根源降低 prompt injection 和敏感内容扩散面。

### 7.3 高风险动作

| 动作 | 是否允许 | 控制要求 |
| --- | --- | --- |
| 从原始资料自动发布 Soul | 否 | 必须真人确认 |
| 在任务运行中改 Soul | 否 | 发布新 persona version，只影响新任务 |
| 把 v1 任务升级到 v2 | 否 | 历史 snapshot 保持不变 |
| 让 Soul 改 Gate 或 Canon | 否 | Workflow 和 Reviewer 权限隔离 |
| 启用时运 overlay | 本轮否 | 未来另立设计、默认关闭、用户显式授权、与 run 一起冻结 |

## 8. 测试、评测与可观测性

### 8.1 自动化测试

实施时至少覆盖：

- `contracts/persona-package.schema.json`
  - v1 manifest 仍能验证历史 snapshot。
  - v2 manifest 只接受 `soul.md`，拒绝混合 L1/L2。
- `tests/test_personas.py`
  - v2 `/persona/soul.md` 等于 snapshot 中 Soul 全文，字节内容不丢失。
  - v2 不再暴露 `/persona/l1-summary.md` 和 `/persona/l2-summary.md`。
  - Soul 超限、hash 不匹配、缺失和待确认均 fail closed。
  - v1 snapshot 恢复时上下文路径和内容保持不变。
- `tests/test_bundled_personas.py`
  - 所有可创建新任务的内置 persona 都迁移到 v2。
  - `project.md` 不复制 Soul 正文。
  - manifest、文件 hash 和 package hash 一致。
- `tests/test_agents.py`
  - 所有模型阶段被要求读取完整 `/persona/soul.md`。
  - 生成阶段明确 Soul 不能覆盖用户、Canon、L0、L4、L3 和 StoryContract。
  - Reviewer 明确不以 Soul 作为硬 Gate。

不新增“某个词出现几次”或“像不像八字/星盘”的字符串测试。这类测试不能证明创作质量，还会诱导模型机械复述人格标签。

### 8.2 隔离真实模型验收

使用相同模型、参数、故事输入、L0/L3/L4 和临时 SQLite 做三组对照：

| 组别 | Persona 输入 | 目的 |
| --- | --- | --- |
| A | 目标 `soul.md` 全文 | 验证目标人格行为 |
| B | 中性 Soul，长度和结构接近 | 排除“多一段 Prompt”本身的影响 |
| C | v1 L1/L2 两份摘要 | 比较合并前后的重复、冲突和稳定性 |

人工检查：

- A 组是否在观察、动作、人物压力、节奏和对白质感上稳定体现 Soul。
- 三组是否同样遵守用户输入、Canon、L0、L4、集数和 StoryContract。
- A 组是否出现术数术语、时间预测、现实人格补造或角色同质化。
- 不同阶段实际接收到的 Soul hash 和字符数是否完全一致。
- Reviewer 是否只引用 L0/L4/Canon 证据，而不是 Soul 偏好。

单次对照只能提供行为证据，不能证明 L1/L2 推演具有事实效度或统计因果关系。

### 8.3 日志与追踪

每次模型调用记录：

```text
persona_schema_version
persona_id
persona_version
persona_snapshot_sha256
soul_sha256
soul_char_count
soul_mount_path=/persona/soul.md
soul_full_text_loaded=true|false
```

不记录：原始 L1/L2 全文、出生资料、被排除的现实建议以及 Soul 正文副本。

## 9. ADR-001：用一个完整 Soul 替代运行时 L1/L2

### 状态

Proposed

### 决策

- 原始 L1、L2 分开保存，只供人工编译和审计。
- persona v2 用 `soul.md` 替代运行时 `l1.md` 与 `l2.md`。
- Soul 是经真人确认、去重和转译后的稳定创作人格。
- 所有模型阶段读取 Soul 全文；不摘要、不检索、不切片、不静默截断。
- 时间预测和现实建议不进入稳定 Soul。
- v1 历史 snapshot 保持旧投影，新任务只使用 v2。
- Soul 是 advisory identity，不是事实、Memory、Skill 或 Gate。

### 正面后果

- 人格从三处潜在真源收敛为一个权威文件。
- 消除 L1/L2 近义内容的重复加权和临场冲突。
- 同一 snapshot 的所有阶段看到完全一致的人格正文。
- 继续复用 manifest、hash、snapshot、只读挂载和现有 L0/L4 Gate。
- 原始隐私和时间预测不进入模型上下文。

### 负面后果

- persona schema 从 v1 升级到 v2，需要迁移内置 persona 和测试。
- 为保证历史任务可恢复，需要保留明确、只读的 v1 snapshot 投影。
- Soul 编译依赖真人判断，不能一次自动导入完成。
- 全文常驻增加固定 token 成本，需要 8,000 字符上限和真实模型验收。

### 中性后果

- v2 运行包从九个 Markdown 文件变为八个。
- L1/L2 原始资料仍然存在，但不属于运行包。
- 更新 Soul 会产生新 persona version 和 snapshot，只影响新任务。

## 10. 实施顺序

1. 从 L1/L2 中建立候选条目、来源和排除项清单。
2. 真人确认稳定创作身份、观察、能量、张力、避免和仲裁内容。
3. 为目标创作者编写 `soul.md`，不复制敏感资料和时间预测。
4. 定义 persona manifest schema `2.0.0` 和版本化文件集合。
5. 让 validator、package hash、snapshot 和 context projector 支持 v2。
6. 保留 v1 snapshot 的原始上下文投影，禁止新任务继续创建 v1 snapshot。
7. 把内置 persona 的 L1/L2 内容一次性编译为 Soul，删除 v2 包中的 `l1.md`、`l2.md`。
8. 更新 `project.md`，只保留 Soul 状态与权限指向。
9. 更新各阶段 Prompt：全文读取 Soul，并明确生成与审核权限。
10. 补 schema、snapshot、context、Agent 和 bundled persona 测试。
11. 运行项目 build、测试和格式检查。
12. 使用隔离 persona、临时 SQLite 和真实模型完成 A/B/C 验收。

本设计只定义实施边界，不在本轮直接修改 persona schema、运行时代码或现有人格包。

## 11. 完成标准

- L1/L2 原文和指纹保持不变，且不进入 persona、snapshot、日志或交付包。
- 新 persona 使用 `schema_version: "2.0.0"`。
- v2 包存在唯一 `soul.md`，不存在 `l1.md` 或 `l2.md`。
- `soul.md` 包含经确认的 L1+L2 稳定创作内容，不含个人资料、推演过程、时间预测和现实建议。
- 所有模型阶段完整读取 `/persona/soul.md`，实际文本与 snapshot 内容一致。
- 不存在 `/persona/l1-summary.md`、`/persona/l2-summary.md` 或运行时动态 Soul 摘要。
- Soul 超过 8,000 字符时 fail closed，不静默截断。
- `project.md` 不复制 Soul 正文。
- Soul 不能覆盖用户要求、Canon、checkpoint、L0、L4、L3、StoryContract 或集数参数。
- L0/L4 Reviewer 不把 Soul 作为通过或拒绝依据。
- v1 历史任务按旧 snapshot 和旧上下文投影恢复，行为不被 v2 改写。
- 新 Soul 版本只影响新任务，旧任务恢复结果不变。
- 隔离真实模型验收没有出现术数术语泄漏、命运预测、现实人格补造、角色同质化或审核越权。

## 12. 后续设计路由

本架构继续采用 Workflow-Agent Hybrid。后续按以下顺序推进：

1. `ado-workflow-design-skill`：把 persona v1/v2 校验、发布、snapshot 绑定和错误状态写成实施级工作流。
2. `ado-workflow-evaluation-skill`：定义 Soul A/B/C 验收样本、评分维度和回归阈值。
3. `ado-agent-security-and-permission-skill`：只有在原始 L1/L2 将进入共享服务或多人环境时，补充来源授权、隐私和访问控制设计。
4. `ado-agent-deployment-and-observability-skill`：实现前定义生产 trace 字段、告警和版本回滚证据。

不需要进入 RAG、Memory 或 Tool 详细设计，因为本方案明确不使用这些组件装配人格。
