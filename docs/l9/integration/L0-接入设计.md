# L0 关键内容提取与最小升级方案

> 状态：讨论稿，只描述功能增量和最小改造，不代表已经实现。
>
> 原始文件：[L0内核母题.md](../L0内核母题.md)
>
> 当前原文指纹：`sha256:1f180bd503f2284ce448cc06cb62f71714f7aef396fcb8e124ede404a5ab0c7e`

## 0. 结论

原始 L0 不修改。L0 的主体是创作提示词资产：母题、A/B/C/D、雷区和温度都进入 Agent 上下文，由模型在不同阶段应用。Pengine 不需要为 L0 重做一套工作流，也不需要新增 Memory、RAG、数据库状态或新的 Agent。

最小方案是：

```text
原始 L0（仅作为人工分析依据）
  -> 人工提取并更新 personas/<creator>/l0.md
  -> 现有 PersonaCatalog 把完整 l0.md 注入所有模型阶段
  -> 各阶段 Prompt 读取完整 L0，并强调当前需要使用的部分
  -> worker 只负责侧面选择和 L0 Gate 证据这两类确定性校验
  -> 继续使用现有 checkpoint、L0 Gate、快照和交付报告
```

改动范围：

- 新建目标创作者的运行版 `personas/<creator>/l0.md`。
- 在 `agents.py` 中补充各阶段的 L0 使用指令。
- 在 `personas.py` 和 `worker.py` 中只增加侧面与 Gate 证据的最小校验。
- 增加对应测试。

第一版明确不改：

- 九文件 persona 协议。
- `contracts/persona-package.schema.json`。
- API 和前端。
- 工作流阶段及顺序。
- 数据库表结构。
- 现有 Agent 数量。
- 现有 `selected_l0_variant`、`selection_rationale`、`GateResult` 对外结构。

领导以后更新 L0 时，由用户明确要求重新读取和分析；我们把变化作为一次新的系统升级处理。

## 1. 从原文提取出的关键内容

### 1.1 唯一母题

> 初心 vs 现实的落差——理想的人 / 情在现实里如何幻灭、又如何坚守。

系统含义：

- 运行版 `l0.md` 必须保留母题原句，并进入每个模型创作和审核阶段。
- 不能被摘要成“理想与现实”“坚持初心”等泛化标签。
- L0 Gate 必须检查作品是否通过核心人物、冲突、选择和结局真正回答了母题。

### 1.2 A/B/C/D 四个侧面

| ID | 题材 | 原文定义 | 选择时的分辨依据 |
| --- | --- | --- | --- |
| A | 群像 / 主旋律 | 一群人在最暗处奔向一点光，明知会碎仍奔 | 群体、向光、明知会碎仍奔 |
| B | 商战 / 正剧 | 守信义、尽责的人，被规则与时代碾成罪人 | 碾力来自规则和时代 |
| C | 人物 / 古装 | 认死理的人跟世界僵着，为一件信的东西不肯改那句台词 | 一个人与世界僵持，不肯改 |
| D | 现实主义 / 当代 | 较真的人被判成病人，最亲的人以“为他好”的名义把他碾成异类 | 碾力来自亲近者的善意和保护 |

在项目中的具体呈现：

1. 用户照常提交故事和创作要求，不需要自己选 A/B/C/D。
2. Story Architect 在现有“确定创作方向”阶段，判断这个故事最适合用哪一个侧面表达母题。
3. 现有创作方向页面直接展示选择和理由，不新增页面或选择器。
4. 选择进入现有 checkpoint；后续大纲、人物、分集和剧本都读取同一个创作方向，Agent 不得自行改成另一个侧面。
5. 最终 L0 Gate 检查成品是否真正按该侧面写成，而不是只检查是否出现了某个关键词。

页面上的示例：

```text
创作方向

选择的 L0 变体：B｜规则与时代

选择理由：
主人公想守住对客户和员工的承诺，但行业规则和时代变化不断把他推向“罪人”的位置。
故事应通过他的选择和代价表现这个冲突，不由人物直接讲解母题。
```

“只选一个”是指确定一条主要的母题表达路径，不是禁止故事出现其他冲突。第一版不做 A/B/C/D 使用次数统计，这不影响母题在单个作品中生效。

### 1.3 雷区

“雷区”不是故事不能写什么，也不是敏感词表；它指的是这位创作者不接受的母题表达方式。

原文里的具体雷区是：

- 不靠旁白解释母题。
- 不靠心理描写把母题说出来。
- 不用端着的文艺腔抒情。
- 母题从可拍的动作和人物拉扯里长出来。

对比示例：

```text
命中雷区：
旁白：“他终于明白，理想在现实面前一文不值，但他仍决定坚守初心。”

符合要求：
他在辞退名单上签了字，却把自己的车钥匙留在桌上，让财务先补发员工工资。
无旁白解释，观众从他的选择和代价看到“幻灭后仍然坚守”。
```

在项目中的具体用法：

1. 运行版 `persona/l0.md` 保存雷区，并由现有 persona 上下文交给大纲、人物、分集和剧本生成 Agent。
2. 生成 Agent 把雷区当成写作约束：出现解释性表达时，改用可拍动作、人物选择和关系冲突表现。
3. 现有 `accepting_l0` 阶段负责最终拦截。Quality Reviewer 必须给出集数或场次、剧本原句、命中的雷区和判断理由，不能只说“文艺腔过重”。
4. 命中雷区时，L0 Gate 返回 `passed=false`，项目保留现有草稿和拒绝证据，不进入 L4 和正式交付。

审核证据的展示示例：

```text
L0 雷区检查：不通过
位置：第 8 集，结尾场
原句：“他终于明白……”
原因：旁白直接解释了母题，没有通过人物行动和代价表现。
```

第一版不做关键词扫描，因为“旁白”、“心理描写”和“文艺腔”是语义问题，不能通过某个词出现几次判定。第一版也不声称能自动修改雷区问题：当前“重试最终审核”只会重新审核同一份内容，不会改写剧本。自动修复如果必要，应作为后续独立能力设计和验收。

### 1.4 温度

原文关键要求：

- 克制的悲怅打底，哀而不伤。
- 不煽、不嚎。
- 暖先到，灾才痛。
- 伤留在留白里，不点破。
- 每集至多一次情绪峰值，峰后必接一拍收。

系统含义：

- 生成端用它约束全片气质和单集节奏。
- Reviewer 检查暖是否在灾难前被建立、是否多峰争抢、峰后是否有收拍、结尾是否留白。
- “悲剧题材”不等于符合温度，“人物哭喊”也不能脱离语境直接判失败。

### 1.5 固定使用顺序

原文要求：

```text
选择一个侧面
  -> 全片由该侧面统摄
  -> 雷区检查
  -> 温度检查
  -> L0 第一验收
  -> 再进行 L4 手艺验收
```

Pengine 已经有 `selecting_l0_variant`、五个创作阶段、`accepting_l0`、`accepting_l4`，顺序不需要重做。需要补的是侧面合法性校验和 Reviewer 的明确审核要求。

### 1.6 L0 的提示词使用方式

所有模型阶段都保留完整 `/persona/l0.md`，不把母题、侧面、雷区和温度拆成四份独立数据。各阶段 Prompt 只需明确当前应重点使用哪一部分：

| 阶段 | 需要读取的 L0 | 当前阶段的重点 |
| --- | --- | --- |
| 确定创作方向 | 完整 L0 | 根据母题和 A/B/C/D 选定本剧的表达路径 |
| 故事大纲 | 完整 L0 + 已选侧面 | 把母题变成主人公、中心冲突、选择、代价和结局 |
| 人物与关系 | 完整 L0 + 已选侧面 | 明确谁承载理想，谁或什么构成现实压力 |
| 分集大纲 | 完整 L0 + 已选侧面 | 分配压力升级、暖意建立、情绪峰值和收拍 |
| 分集剧本 | 完整 L0 + 已选侧面 | 重点执行雷区和温度，用可拍动作、选择和关系拉扯表达母题 |
| L0 审核 | 完整 L0 + 所有已批准作品 | 按母题兑现、侧面、雷区和温度给出具体证据 |
| L4 审核 | 保留 L0 上下文 | 只审核 L4 技艺，不重新选择或修改 L0 |

因此，“全阶段带入”和“分阶段使用”不冲突：全阶段都能看到完整 L0，但当前 Prompt 告诉 Agent 此时应该如何使用它。

L0 中适合进入提示词的是创作内容：母题原句、侧面及区分、雷区、温度和创作使用顺序。文档来历、归属说明、更新权和台账统计不是创作提示词，不需要反复强调给每个 Agent。

| DeliveryReport | 已包含侧面、理由和 L0 Gate | 保持 API 输出不变 |

## 3. 原始 L0 如何进入系统

原始 L0 不是运行时输入，也不需要程序解析它的自然段、表格或排版。

接入时由人工从原文提取已确认的母题原句、A/B/C/D 及区分、雷区、温度和创作使用顺序，写入目标创作者 persona 的 `l0.md`。这份运行版就是 L0 的提示词资产，继续使用现有九文件格式、manifest 和 snapshot 机制。

为了让系统能校验选择，运行版变体需要保留明确的侧面编号，例如：

```text
- [ID:A][真人已定][归属：源] 一群人在最暗处奔向一点光，明知会碎仍奔
```

这不是自动理解原文，只是让现有 `PersonaCatalog` 读取已确认的运行规则。领导以后更新原文时，再由人重新分析并决定运行版和代码需要改什么。

## 4. 提示词主接入和两个辅助护栏

### 4.1 `personas/<creator>/l0.md`：核心提示词资产

运行版 `l0.md` 保留所有与创作有关的 L0 内容：

- 母题原句。
- A/B/C/D 的完整定义与分辨方法。
- 雷区与正向替代方式。
- 温度和单集情绪纪律。
- 它们在创作与验收中的使用顺序。

当前 `_project_stage_context()` 已经把完整 `/persona/l0.md` 放入每个阶段上下文，所以这部分不需要新增注入模块或拆成多份文件。

### 4.2 `agents.py`：按阶段说明如何使用 L0

最小改动：

1. 每个创作 Agent 都必须读取完整 `/persona/l0.md`。
2. 阶段 Prompt 按 1.6 的表格强调当前任务，不在代码中复制 L0 原文。
3. Story Architect 在选择阶段返回准确的侧面和选择理由。
4. 后续 Agent 同时读取完整 L0 和 checkpoint 中的已选侧面，把母题、雷区和温度真正落到当前产物。
5. Quality Reviewer 在 `accepting_l0` 阶段按“母题兑现、侧面、雷区、温度”给出具体证据。

不为 L0 新增 Agent，不把温度或雷区写成 Python 业务规则。

### 4.3 `personas.py` 和 `worker.py`：只保留确定性护栏

`personas.py` 的最小改动：

1. 保留现有 `_validate_l0_markers()` 和 persona 装载流程。
2. 从运行版 `l0.md` 的变体列表读取已确认的 ID；无显式 ID 的旧 persona 仍使用其完整变体文本。
3. 将允许值交给 Worker，不解析领导原文。

保持不变：

- persona manifest。
- 九文件数量和路径。
- snapshot hash 规则。
- `/persona/l0.md` 注入方式。
- L1–L6 处理逻辑。

现有 `approve_stage()` 是最小接入点。

当阶段为 `SELECTING_L0_VARIANT` 时：

1. 从 `PersonaCatalog` 取得当前运行版 `l0.md` 的允许值。
2. 校验模型返回的侧面是否在允许值内。
3. 非法值不写 checkpoint，按现有结构化输出失败机制处理。
4. 合法值按原有 payload 写入 durable checkpoint。

当阶段为 `ACCEPTING_L0` 且 `passed=true` 时：

1. 检查 evidence 是否包含“母题兑现、侧面、雷区、温度”四部分。
2. evidence 缺少“母题兑现、侧面、雷区、温度”任一部分时不批准 checkpoint。
3. evidence 完整时继续使用现有 Gate 和 checkpoint 流程。

Checkpoint 已经和当前 run、persona snapshot 绑定，所以不新增数据库表，也不重新设计恢复流程。

保持不变：

- Agent 数量。
- Supervisor 路由。
- 五个创作阶段。
- `StoryArchitectResult`。
- `QualityReviewerResult`。
- L0/L4 Gate 顺序。

## 6. 测试范围

现有测试只做少量补充：

- `tests/test_personas.py`：完整 `/persona/l0.md` 仍进入每个模型阶段，且能读取 A/B/C/D，旧 persona 仍可装载。
- `tests/test_worker.py`：非法侧面不能写 checkpoint，合法侧面沿用现有流程。
- `tests/test_agents.py`：各阶段提示词明确读取 L0 并应用当前重点；L0 Gate evidence 包含母题、侧面、雷区和温度。

真实模型验收继续复用现有 `tests/live/test_real_model_e2e.py`，使用隔离 persona 和数据库验证一次合法选择、一次非法选择拒绝和一次 L0 Gate。

## 7. 领导更新文档时的升级方式

由用户明确触发：提供或指定更新后的 L0，并要求重新分析。

```text
读取新原文
  -> 人工对比并输出变化和影响模块
  -> 人工确认升级范围
  -> 必要时修改 persona、Prompt、校验逻辑和测试
  -> 更新 persona/l0.md 及 manifest hash
  -> 生成新 persona snapshot
  -> 隔离真实模型验收
  -> 新任务使用新版本
```

变化与最小升级范围：

| 原文变化 | 最小系统升级 |
| --- | --- |
| 只改措辞，结构和语义不变 | 更新 `l0.md`、manifest hash 和回归快照；模块无需改动 |
| 修改 A/B/C/D | 更新运行版 `l0.md`、选择测试和 Agent 对照用例 |
| 修改雷区或温度的具体内容 | 只更新运行版 `l0.md` 和 Reviewer 回归用例 |
| 修改雷区或温度的阶段使用方式 | 再更新相关阶段 Prompt 说明 |
| 增加新的机器读法 | 确认业务必要性后，再扩展运行版标记和读取逻辑 |
| 修改使用顺序 | 才考虑改 Worker/Workflow；不提前预留复杂状态 |

历史任务不迁移、不覆盖，继续使用创建时的 persona snapshot。

## 8. 实施顺序

1. 人工提取 L0 创作内容，建立目标创作者的运行版 `l0.md`。
2. 在 `agents.py` 中让各阶段提示词明确读取完整 L0，并说明当前阶段的使用重点。
3. 在 `personas.py` 读取运行版的侧面 ID，保持旧 persona 兼容。
4. 在 `worker.py` 增加选择值和 Gate 证据校验。
5. 跑现有 persona、worker、agent 和集成测试，确认旧 persona 不受影响。
6. 使用新建的目标 persona 和隔离数据库执行真实模型验收。

完成标准：

- 原始 L0 指纹不变。
- 领导原文不直接作为运行时 `l0.md`。
- 经人工确认的运行版 `l0.md` 可被现有 persona 机制装载。
- 每个模型创作和审核阶段都能读取完整 L0，并按阶段指令使用。
- 四个现有 persona 无需迁移。
- A/B/C/D 之外的选择不能进入 checkpoint。
- 后续阶段继续使用现有 snapshot 和 checkpoint。
- L0 Gate 明确审核母题、侧面、雷区和温度。
- API、前端、数据库 schema 和工作流阶段无变化。

## 9. 本轮最终方案

当前 L0 不新增独立模块。运行版 `l0.md` 是核心，提示词路由是主接入，程序校验是辅助护栏：

```text
personas/<creator>/l0.md（完整创作提示词）
  -> 现有 PersonaCatalog（全阶段注入）
  -> agents.py（按阶段说明使用重点）
  -> personas.py + worker.py（侧面与 Gate 证据护栏）
```

其余系统继续复用。未来文档更新时，先人工分析变化；只有新原文确实引入新的运行要求，才改对应模块。
