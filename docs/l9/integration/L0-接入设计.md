# L0 关键内容提取与最小升级方案

> 状态：讨论稿，只描述功能增量和最小改造，不代表已经实现。
>
> 原始文件：[L0内核母题.md](../L0内核母题.md)
>
> 当前原文指纹：`sha256:1f180bd503f2284ce448cc06cb62f71714f7aef396fcb8e124ede404a5ab0c7e`

## 0. 结论

原始 L0 不修改。Pengine 不需要为 L0 重做一套工作流，也不需要新增 Memory、RAG、数据库状态或新的 Agent。

最小方案是：

```text
原始 L0（仅作为人工分析依据）
  -> 人工提取并更新 persona/<creator>/l0.md
  -> 现有 PersonaCatalog 校验、快照和注入
  -> worker 校验侧面选择和 L0 Gate 证据
  -> Agent 按 L0 生成与审核
  -> 继续使用现有 checkpoint、L0 Gate、快照和交付报告
```

改动范围：

- 修改三个现有模块：`personas.py`、`worker.py`、`agents.py`。
- 增加对应测试。

第一版明确不改：

- 九文件 persona 协议。
- `contracts/persona-package.schema.json`。
- API 和前端。
- 工作流阶段及顺序。
- 数据库表结构。
- 现有 Agent 数量。
- 现有 `selected_l0_variant`、`selection_rationale`、`GateResult` 对外结构。

领导以后更新 L0 时，由用户明确要求重新读取和分析；我们把变化作为一次新的系统升级处理。

## 1. 从原文提取出的关键内容

### 1.1 唯一母题

> 初心 vs 现实的落差——理想的人 / 情在现实里如何幻灭、又如何坚守。

系统含义：

- 母题原文必须进入每个创作阶段。
- 不能被摘要成“理想与现实”“坚持初心”等泛化标签。
- L0 Gate 必须检查作品是否通过核心人物、冲突、选择和结局真正回答了母题。

### 1.2 A/B/C/D 四个侧面

| ID | 题材 | 原文定义 | 选择时的分辨依据 |
| --- | --- | --- | --- |
| A | 群像 / 主旋律 | 一群人在最暗处奔向一点光，明知会碎仍奔 | 群体、向光、明知会碎仍奔 |
| B | 商战 / 正剧 | 守信义、尽责的人，被规则与时代碾成罪人 | 碾力来自规则和时代 |
| C | 人物 / 古装 | 认死理的人跟世界僵着，为一件信的东西不肯改那句台词 | 一个人与世界僵持，不肯改 |
| D | 现实主义 / 当代 | 较真的人被判成病人，最亲的人以“为他好”的名义把他碾成异类 | 碾力来自亲近者的善意和保护 |

系统含义：

- 每单必须选择且只能选择一个侧面。
- 选择值必须来自当前 L0，不允许模型创造 E 或新名称。
- 选定后整单固定，后续阶段不能漂移。
- 侧面使用分布只用于观察，不能为了均衡而强迫错误选择。

### 1.3 雷区

原文关键要求：

- 不靠旁白解释母题。
- 不靠心理描写把母题说出来。
- 不用端着的文艺腔抒情。
- 母题从可拍的动作和人物拉扯里长出来。

系统含义：生成端始终看到这些约束，L0 Reviewer 检查作品是否“用剧情表达”而不是“用语言解释”。

第一版不做关键词拦截器。旁白、心理描写和文艺腔都依赖语境，粗暴扫描容易误伤正常台词和剧作形式。先使用现有语义 Reviewer，并用真实失败案例决定以后是否值得增加确定性检测。

### 1.4 温度

原文关键要求：

- 克制的悲怅打底，哀而不伤。
- 不煽、不嚎。
- 暖先到，灾才痛。
- 伤留在留白里，不点破。
- 每集至多一次情绪峰值，峰后必接一拍收。

系统含义：

- 生成端用它约束全片气质和单集节奏。
- Reviewer 检查暖是否在灾难前被建立、是否多峰争抢、峰后是否有收拍、结尾是否留白。
- “悲剧题材”不等于符合温度，“人物哭喊”也不能脱离语境直接判失败。

### 1.5 固定使用顺序

原文要求：

```text
选择一个侧面
  -> 全片由该侧面统摄
  -> 雷区检查
  -> 温度检查
  -> L0 第一验收
  -> 再进行 L4 手艺验收
```

Pengine 已经有 `selecting_l0_variant`、五个创作阶段、`accepting_l0`、`accepting_l4`，顺序不需要重做。需要补的是侧面合法性校验和 Reviewer 的明确审核要求。

## 2. 可以直接复用的现有能力

| 现有能力 | 当前作用 | 最小方案如何复用 |
| --- | --- | --- |
| 九文件 persona 包 | 保存运行版 `l0.md` 并参与 package hash | 保持现有格式；领导原文不直接进入运行时 |
| Persona snapshot | 每个任务绑定不可变人格版本 | 直接承担 L0 版本冻结，不新增独立 L0 版本表 |
| `/persona/l0.md` | 已注入所有创作和审核阶段 | 保持不变，不新增上下文文件 |
| `selecting_l0_variant` | 已让 Agent 返回侧面和理由 | 保持现有输出字段，只增加返回值校验 |
| Durable checkpoint | 已保存选择阶段结果 | 直接作为本单 L0 绑定，不新增 `l0_bindings` 表 |
| `accepting_l0` | 已有独立 L0 Gate | 保持现有 `passed + evidence` 结构，只规范 evidence 内容 |
| `accepting_l4` | 已在 L0 Gate 后执行 | 保持现有阶段和顺序 |
| DeliveryReport | 已包含侧面、理由和 L0 Gate | 保持 API 输出不变 |

## 3. 原始 L0 如何进入系统

原始 L0 不是运行时输入，也不需要程序解析它的自然段、表格或排版。

接入时由人工从原文提取已确认的母题、A/B/C/D、雷区和温度，写入目标创作者 persona 的 `l0.md`。该运行版继续使用现有九文件格式、manifest 和 snapshot 机制。

为了让系统能校验选择，运行版变体需要保留明确的侧面编号，例如：

```text
- [ID:A][真人已定][归属：源] 一群人在最暗处奔向一点光，明知会碎仍奔
```

这不是自动理解原文，只是让现有 `PersonaCatalog` 读取已确认的运行规则。领导以后更新原文时，再由人重新分析并决定运行版和代码需要改什么。

## 4. 三个最小接入点

### 4.1 `personas.py`：读取运行版侧面

最小改动：

1. 保留现有 `_validate_l0_markers()` 和 persona 装载流程。
2. 从运行版 `l0.md` 的变体列表读取已确认的 ID；无显式 ID 的旧 persona 仍使用其完整变体文本。
3. 将允许值交给 Worker，不解析领导原文。

保持不变：

- persona manifest。
- 九文件数量和路径。
- snapshot hash 规则。
- `/persona/l0.md` 注入方式。
- L1–L6 处理逻辑。

### 4.2 `worker.py`：checkpoint 前校验一次

现有 `approve_stage()` 是最小接入点。

当阶段为 `SELECTING_L0_VARIANT` 时：

1. 从 `PersonaCatalog` 取得当前运行版 `l0.md` 的允许值。
2. 校验模型返回的侧面是否在允许值内。
3. 非法值不写 checkpoint，按现有结构化输出失败机制处理。
4. 合法值按原有 payload 写入 durable checkpoint。

当阶段为 `ACCEPTING_L0` 且 `passed=true` 时：

1. 检查 evidence 是否包含“母题兑现、雷区、温度”三部分。
2. evidence 缺少“母题兑现、雷区、温度”任一部分时不批准 checkpoint。
3. evidence 完整时继续使用现有 Gate 和 checkpoint 流程。

Checkpoint 已经和当前 run、persona snapshot 绑定，所以不新增数据库表，也不重新设计恢复流程。

### 4.3 `agents.py`：收紧两个提示

最小改动：

1. Story Architect 在选择阶段必须从 `/persona/l0.md` 返回准确 ID 或准确变体值，不得重命名。
2. Quality Reviewer 在 `accepting_l0` 阶段按“母题兑现、雷区、温度”三段写 evidence；具体内容仍从 `/persona/l0.md` 和已批准作品中读取。

保持不变：

- Agent 数量。
- Supervisor 路由。
- 五个创作阶段。
- `StoryArchitectResult`。
- `QualityReviewerResult`。
- L0/L4 Gate 顺序。

## 5. 第一版不需要改动的模块

| 模块 | 不改原因 |

| `schemas.py` | 现有字符串选择和 `passed + evidence` 足以承载第一版；在应用层加强校验即可 |

## 6. 测试范围

现有测试只做少量补充：

- `tests/test_personas.py`：能从运行版读取 A/B/C/D，旧 persona 仍可装载。
- `tests/test_worker.py`：非法侧面不能写 checkpoint，合法侧面沿用现有流程。
- `tests/test_agents.py`：选择提示不允许重命名；L0 Gate evidence 包含母题、雷区、温度三段。

真实模型验收继续复用现有 `tests/live/test_real_model_e2e.py`，使用隔离 persona 和数据库验证一次合法选择、一次非法选择拒绝和一次 L0 Gate。

## 7. 领导更新文档时的升级方式

由用户明确触发：提供或指定更新后的 L0，并要求重新分析。

```text
读取新原文
  -> 人工对比并输出变化和影响模块
  -> 人工确认升级范围
  -> 必要时修改 persona、Prompt、校验逻辑和测试
  -> 更新 persona/l0.md 及 manifest hash
  -> 生成新 persona snapshot
  -> 隔离真实模型验收
  -> 新任务使用新版本
```

变化与最小升级范围：

| 原文变化 | 最小系统升级 |
| --- | --- |
| 只改措辞，结构和语义不变 | 更新 `l0.md`、manifest hash 和回归快照；模块无需改动 |
| 修改 A/B/C/D | 更新运行版 `l0.md`、选择测试和 Agent 对照用例 |
| 修改雷区或温度 | 更新 `review_instruction()` 及 Reviewer 回归用例 |
| 增加新的机器读法 | 确认业务必要性后，再扩展运行版标记和读取逻辑 |
| 修改使用顺序 | 才考虑改 Worker/Workflow；不提前预留复杂状态 |

历史任务不迁移、不覆盖，继续使用创建时的 persona snapshot。

## 8. 实施顺序

1. 人工提取 L0 关键规则，建立目标创作者的运行版 `l0.md`。
2. 在 `personas.py` 读取运行版的侧面 ID，保持旧 persona 兼容。
3. 在 `worker.py` 增加选择值和 Gate 证据校验。
4. 在 `agents.py` 收紧选择和审核提示。
5. 跑现有 persona、worker、agent 和集成测试，确认旧 persona 不受影响。
6. 使用新建的目标 persona 和隔离数据库执行真实模型验收。

完成标准：

- 原始 L0 指纹不变。
- 领导原文不直接作为运行时 `l0.md`。
- 经人工确认的运行版 `l0.md` 可被现有 persona 机制装载。
- 四个现有 persona 无需迁移。
- A/B/C/D 之外的选择不能进入 checkpoint。
- 后续阶段继续使用现有 snapshot 和 checkpoint。
- L0 Gate 明确审核母题、雷区、温度。
- API、前端、数据库 schema 和工作流阶段无变化。

## 9. 本轮最终方案

当前 L0 不新增独立模块，只在现有三个位置做最小改造：

```text
personas.py（读取运行版侧面）
  -> worker.py（选择和 Gate 证据校验）
  -> agents.py（生成与审核约束）
```

其余系统继续复用。未来文档更新时，先人工分析变化；只有新原文确实引入新的运行要求，才改对应模块。
