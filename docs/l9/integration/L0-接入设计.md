> 原始文件：[L0内核母题.md](../L0内核母题.md)

## 0. 这份文档解决什么问题

原始 L0 不修改。我们从原文提取系统必须执行的内容，再把它们对应到 Pengine 的功能和代码模块中。

以后领导更新 L0 时，处理方式不是让系统自动学习，也不是覆盖旧内容，而是发起一次新的系统升级：重新读取新原文、比较变化、分析影响、修改功能或规则、补测试、生成新版本。历史任务继续使用历史快照。

固定原则：

1. 原始 L0 是唯一权威来源。
2. 系统只能读取、编译和执行，不能反向修改原文。
3. 本文只描述从当前 L0 得出的系统能力，不延伸领导没有写过的新规则。
4. 用户反馈、模型输出、侧面统计都不能更新 L0。
5. 领导以后更新原文，必须经过一次显式升级流程才能进入新任务。

## 2. 从原文提取出的系统功能

### 2.1 F-L0-01：L0 原文版本与编译

原文要求：

- 母题一句话必须全文注入，不作摘要、不作省略。
- 变体、雷区、温度需要转换成机器可读形态。
- 原文更新只能由源本人发起，历史任务保留旧版本。

需要增加：

1. 为原始 L0 计算内容指纹。
2. 保存原文版本、生效时间、批准状态和来源路径。
3. 从已批准原文生成结构化 `L0Policy`：
   - `theme`：完整母题原文。
   - `variants`：A/B/C/D 及题材、定义、分辨依据、状态。
   - `redlines`：雷区原文和审核规则。
   - `temperature`：基调、峰值和收拍规则。
   - `ownership`：归属、只读和更新权。
   - `source_sha256`：原文指纹。
4. 生成符合现有 persona 包格式的运行时 `l0.md`。
5. 每个派生字段都能定位到原文段落，不能由模型自由改写。

当前原文不能直接替换 persona 包中的 `l0.md`：原文使用表格和自然段，而当前校验器要求变体、雷区、温度使用带归属和状态标记的列表。正确做法是增加编译层生成运行投影，而不是修改原文迎合校验器。

### 2.2 F-L0-02：封闭的 A/B/C/D 侧面选择

当前原文定义：

| ID | 题材 | 侧面定义 | 选择时的核心分辨 |
| --- | --- | --- | --- |
| A | 群像 / 主旋律 | 一群人在最暗处奔向一点光，明知会碎仍奔 | 群体、向光、明知会碎仍奔 |
| B | 商战 / 正剧 | 守信义、尽责的人，被规则与时代碾成罪人 | 碾力来自规则和时代 |
| C | 人物 / 古装 | 认死理的人跟世界僵着，为一件信的东西不肯改那句台词 | 一个人与世界僵持，不肯改 |
| D | 现实主义 / 当代 | 较真的人被判成病人，最亲的人以“为他好”的名义把他碾成异类 | 碾力来自亲近者的善意和保护 |

现有问题：

- `selected_l0_variant` 只要求是非空文本。
- 模型可以返回“A/B/C/D”之外的新名字，系统仍可能接受。
- 选择结果没有显式绑定当前 L0 版本。

需要改造：

1. Agent 返回 `variant_id` 和 `selection_rationale`，不再自己创造侧面名称。
2. Workflow 在进入故事大纲前校验：
   - `variant_id` 属于当前 `L0Policy.variants`。
   - 该变体状态为已批准。
   - 选择绑定当前 `source_sha256` 和 persona snapshot。
3. 校验通过后生成不可变的 `TaskL0Binding`。
4. 故事大纲、人物小传、人物关系、分集大纲、分集剧本和最终 Reviewer 全部读取同一个绑定。
5. 修订任务默认继承原任务的 L0 版本；是否允许重新选侧面，应由修订合同明确控制，不能由模型临时决定。

侧面分布只能作为运营观察信息，不能为了“均衡”强迫新任务选择不匹配的低频侧面。

### 2.3 F-L0-03：雷区规则

原文关键内容：

- 不用旁白把母题解释出来。
- 不靠心理描写把理想与现实的撕裂讲出来。
- 不用端着的文艺腔抒情。
- 母题应从可拍的动作和人物拉扯里长出来。

需要增加两层检查：

#### 第一层：确定性候选检测

- 区分场景说明、动作、旁白和台词。
- 标出疑似集中解释、连续心理独白、直接点题的段落。
- 台词不能仅因包含某个词就自动失败。
- 检测结果只是候选证据，不能独立判定“文艺腔”。

#### 第二层：L0 语义审核

Reviewer 判断：

1. 母题主要通过动作、选择、关系和后果体现，还是靠角色/旁白直接解释。
2. 被标记段落是否真的把母题说破。
3. 删除说理文字后，剧情本身能否仍然表达选定侧面。

审核失败必须返回具体集、场和原文片段，不能只写“过于文艺”或“缺少行动”。

### 2.4 F-L0-04：温度规则

原文关键内容：

- 克制的悲怅打底，哀而不伤。
- 不煽、不嚎。
- 暖先到，灾才痛。
- 伤留在留白里，不点破。
- 每集至多一次情绪峰值，峰后必接一拍收。

需要增加：

1. 生成阶段始终携带温度规则。
2. 分集大纲明确每集的主要情绪峰值和收拍位置。
3. 分集剧本审核每集是否出现多个竞争峰值。
4. Reviewer 检查“暖”是否在“灾”之前被实际建立，而不是结尾补一句说明。
5. Reviewer 检查结尾是否通过动作、画面或未说完的话形成留白。
6. 不能把“悲剧题材”直接当成符合温度，也不能把“人物哭喊”直接当成不符合；必须看具体执行。

### 2.5 F-L0-05：L0 第一验收闸

原文要求：L0 验收先于任何手艺层面的验收。

当前已有 `accepting_l0` 和 `accepting_l4` 两个阶段，顺序基础是对的，但 L0 Gate 结果只有统一的 `passed + evidence`。

需要把 L0 Gate 拆成三个明确结论：

| 审核维度 | 必须回答的问题 | 证据要求 |
| --- | --- | --- |
| `theme_alignment` | 成片是否真正回答了本单选择的侧面 | 引用贯穿主因果的关键集和场 |
| `redline_compliance` | 是否依靠旁白、心理解释或端腔抒情说破母题 | 引用风险片段；说明为什么构成或不构成雷区 |
| `temperature_compliance` | 是否符合克制、暖先到灾才痛、峰后收拍和留白 | 按集提供关键峰值与收拍证据 |

三个维度全部通过，L0 Gate 才通过。通过后才能进入 L4 Gate。

“作品体现了初心与现实”这种自我声明不能作为 Gate 证据。

### 2.6 F-L0-06：侧面台账与分布统计

原文要求：保存每单选择的侧面和理由，并查看跨任务分布。

需要增加每单一条不可变记录：

- creation/run ID。
- persona ID 和 snapshot hash。
- L0 source hash。
- variant ID。
- 选择理由。
- 初始任务或修订任务。
- 选择时间和最终状态。

统计功能只需要回答：

- A/B/C/D 各使用多少次。
- 最近一段时间是否长期集中在单一侧面。
- 哪些任务在 L0 Gate 被拒绝，拒绝原因属于哪个维度。

系统只能呈现统计和风险提示。是否调整选侧倾向，由真人根据作品判断；不能自动修改 L0 或选择权重。

### 2.7 F-L0-07：L0 文档升级

领导以后更新原始 L0 时，系统按一次版本升级处理。

触发方式：用户明确提供或指定新的 L0 文件，并要求重新分析。系统不后台监控，不自动吸收文件变化。

升级步骤：

```text
读取新原文
  -> 计算新指纹
  -> 与当前批准版本做语义差异分析
  -> 判断影响到哪些功能和测试
  -> 形成升级清单
  -> 人工确认
  -> 修改编译、规则、Workflow、Reviewer 或统计
  -> 生成新的 persona/L0 版本和快照
  -> 隔离真实模型验收
  -> 新任务切换到新版本
```

历史任务不迁移、不重写，继续使用创建时的 L0 快照。

不同原文变化对应的系统升级：

| 原文变化 | 系统升级内容 |
| --- | --- |
| 只修改表述，不改变含义 | 更新来源版本和运行投影，执行现有回归测试 |
| 修改母题 | 重大升级：重新检查全部变体、生成约束、L0 Gate 和对照用例 |
| 新增、删除或修改侧面 | 修改变体枚举、选择校验、台账展示和侧面测试 |
| 修改雷区 | 修改候选检测、Reviewer rubric 和误报/漏报用例 |
| 修改温度 | 修改生成约束、分集结构和温度审核用例 |
| 修改创作使用顺序 | 修改 Workflow 状态机和恢复逻辑 |
| 修改归属、只读或更新权 | 修改审批、权限、审计和发布流程 |
| 新增机器消费方式 | 新增对应系统功能，不能把新内容硬塞进现有 Prompt |

如果新原文与现有系统行为冲突，升级必须暂停并明确冲突，不能静默选择旧规则或新规则。

## 3. 对 Pengine 模块的具体改造

| 模块 | 需要改造的内容 |
| --- | --- |
| `src/pengine/l0_policy.py`（新增） | 定义 L0 编译结果；从批准原文提取母题、变体、雷区、温度、归属和来源位置；不负责生成创意内容 |
| `src/pengine/personas.py` | 在 persona 校验/快照阶段生成并缓存 `L0Policy`；运行上下文继续注入 L0，但必须绑定来源指纹 |
| `contracts/persona-package.schema.json` | 第一版保留九文件协议；补充 L0 来源/版本约束时，应通过现有 manifest 或内容寻址元数据设计，不直接把任意新文件塞进 persona 包 |
| `src/pengine/schemas.py` | 将自由文本选择升级为带 `variant_id`、L0 版本和来源指纹的结构；为 L0 Gate 增加三个审核维度 |
| `src/pengine/agents.py` | Selector 只能从当前变体集合选择；生成 Agent 读取冻结绑定；L0 Reviewer 按母题、雷区、温度分别返回证据 |
| `src/pengine/worker.py` | 在选择结果进入 checkpoint 前执行枚举和版本校验；后续阶段只使用冻结的 `TaskL0Binding`；保证 L0 Gate 先于 L4 Gate |
| `src/pengine/repository.py` | 持久化任务 L0 绑定和侧面台账；历史运行保持原 snapshot；支持按版本、侧面和 Gate 结果查询 |
| `src/pengine/observability.py` | 记录 L0 版本、侧面、选择失败、三个 Gate 维度和分布指标；不记录原文全文到外部日志 |
| `tests/test_personas.py` | 验证原文编译、来源追溯、非法结构拒绝、历史版本可回放 |
| `tests/test_agents.py` | 验证 A/B/C/D 封闭选择、非法侧面拒绝、生成阶段绑定不漂移、Reviewer 证据合同 |
| `tests/test_repository.py` | 验证绑定、台账、版本隔离和统计数据不反写 L0 |
| `tests/live/test_real_model_e2e.py` | 用隔离 persona 和数据库证明真实模型读取当前 L0、选择合法侧面并通过真实 Gate |

## 4. 推荐实施顺序

### 第一步：原文编译与版本

实现 F-L0-01。先解决“原文不改，但系统能稳定读取”的问题。

验收：

- 原始文件指纹不变。
- 所有派生字段都能定位回原文。
- 原文表格能生成符合 persona 合同的运行投影。
- 同一原文多次编译结果完全一致。

### 第二步：侧面选择与整单绑定

实现 F-L0-02。

验收：

- A/B/C/D 可以通过。
- 任意新名字不能进入故事大纲阶段。
- 五个创作阶段读取同一个 L0 版本和侧面。
- 恢复、重试和修订不会无意改变绑定。

### 第三步：雷区、温度与 L0 Gate

实现 F-L0-03、F-L0-04、F-L0-05。

验收：

- Reviewer 分别返回母题、雷区、温度结论。
- 空泛自述不能通过。
- 误报候选不会被确定性规则直接判死。
- L0 Gate 不通过时，L4 Gate 不执行。

### 第四步：台账与统计

实现 F-L0-06。

验收：

- 每单只有一个当前有效绑定。
- 能按 L0 版本和侧面查询任务。
- 统计不会修改下一单选择或人格资产。

### 第五步：固化升级机制

实现 F-L0-07 的版本和验收流程。

验收：

- 新 L0 发布后只影响新任务。
- 历史任务仍能按旧快照回放。
- 每一种原文变化都能得到明确的影响清单。
- 未经人工确认的新版本不能激活。

## 5. 当前明确不做的事

- 不修改领导的原始 L0。
- 不把 L0 存入 Memory。
- 不把 L0 做成按需 RAG。
- 不允许模型创建新的侧面。
- 不根据用户反馈自动更新 L0。
- 不根据侧面分布自动调权。
- 不在这一步改造 L1–L6。
- 不在领导更新文件后自动上线；每次都重新读取、分析、实施和验收。

## 6. 本轮结论

当前 L0 对 Pengine 产生七项系统升级：

1. L0 原文版本与编译。
2. A/B/C/D 封闭选择。
3. 整单不可变的 L0 绑定。
4. 雷区规则。
5. 温度规则和三维 L0 Gate。
6. 侧面台账与分布统计。
7. 文档更新驱动的显式系统升级机制。

这七项是从当前原文直接提取出来的。以后原文新增或修改内容时，再重新分析它带来的功能增量，不提前猜测、不自动学习。
