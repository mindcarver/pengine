# L0 关键内容提取与最小升级方案

> 状态：讨论稿，只描述功能增量和最小改造，不代表已经实现。
>
> 原始文件：[L0内核母题.md](../L0内核母题.md)
>
> 当前原文指纹：`sha256:1f180bd503f2284ce448cc06cb62f71714f7aef396fcb8e124ede404a5ab0c7e`

## 0. 结论

原始 L0 不修改。Pengine 不需要为 L0 重做一套工作流，也不需要新增 Memory、RAG、数据库状态或新的 Agent。

最小方案是：

```text
原始 L0 / persona l0.md
  -> 新增 l0_policy.py
     - 解析原文
     - 校验 A/B/C/D
     - 校验 L0 Gate 证据格式
     - 汇总已有侧面记录
     - 比较新旧 L0 的升级影响
  -> 接入现有 persona、worker、Agent
  -> 继续使用现有 checkpoint、L0 Gate、快照和交付报告
```

改动范围：

- 新增一个模块：`src/pengine/l0_policy.py`。
- 修改三个现有模块：`personas.py`、`worker.py`、`agents.py`。
- 增加对应测试。

第一版明确不改：

- 九文件 persona 协议。
- `contracts/persona-package.schema.json`。
- API 和前端。
- 工作流阶段及顺序。
- 数据库表结构。
- 现有 Agent 数量。
- 现有 `selected_l0_variant`、`selection_rationale`、`GateResult` 对外结构。

领导以后更新 L0 时，由用户明确要求重新读取和分析；我们把变化作为一次新的系统升级处理。

## 1. 从原文提取出的关键内容

### 1.1 唯一母题

> 初心 vs 现实的落差——理想的人 / 情在现实里如何幻灭、又如何坚守。

系统含义：

- 母题原文必须进入每个创作阶段。
- 不能被摘要成“理想与现实”“坚持初心”等泛化标签。
- L0 Gate 必须检查作品是否通过核心人物、冲突、选择和结局真正回答了母题。

### 1.2 A/B/C/D 四个侧面

| ID | 题材 | 原文定义 | 选择时的分辨依据 |
| --- | --- | --- | --- |
| A | 群像 / 主旋律 | 一群人在最暗处奔向一点光，明知会碎仍奔 | 群体、向光、明知会碎仍奔 |
| B | 商战 / 正剧 | 守信义、尽责的人，被规则与时代碾成罪人 | 碾力来自规则和时代 |
| C | 人物 / 古装 | 认死理的人跟世界僵着，为一件信的东西不肯改那句台词 | 一个人与世界僵持，不肯改 |
| D | 现实主义 / 当代 | 较真的人被判成病人，最亲的人以“为他好”的名义把他碾成异类 | 碾力来自亲近者的善意和保护 |

系统含义：

- 每单必须选择且只能选择一个侧面。
- 选择值必须来自当前 L0，不允许模型创造 E 或新名称。
- 选定后整单固定，后续阶段不能漂移。
- 侧面使用分布只用于观察，不能为了均衡而强迫错误选择。

### 1.3 雷区

原文关键要求：

- 不靠旁白解释母题。
- 不靠心理描写把母题说出来。
- 不用端着的文艺腔抒情。
- 母题从可拍的动作和人物拉扯里长出来。

系统含义：生成端始终看到这些约束，L0 Reviewer 检查作品是否“用剧情表达”而不是“用语言解释”。

第一版不做关键词拦截器。旁白、心理描写和文艺腔都依赖语境，粗暴扫描容易误伤正常台词和剧作形式。先使用现有语义 Reviewer，并用真实失败案例决定以后是否值得增加确定性检测。

### 1.4 温度

原文关键要求：

- 克制的悲怅打底，哀而不伤。
- 不煽、不嚎。
- 暖先到，灾才痛。
- 伤留在留白里，不点破。
- 每集至多一次情绪峰值，峰后必接一拍收。

系统含义：

- 生成端用它约束全片气质和单集节奏。
- Reviewer 检查暖是否在灾难前被建立、是否多峰争抢、峰后是否有收拍、结尾是否留白。
- “悲剧题材”不等于符合温度，“人物哭喊”也不能脱离语境直接判失败。

### 1.5 固定使用顺序

原文要求：

```text
选择一个侧面
  -> 全片由该侧面统摄
  -> 雷区检查
  -> 温度检查
  -> L0 第一验收
  -> 再进行 L4 手艺验收
```

Pengine 已经有 `selecting_l0_variant`、五个创作阶段、`accepting_l0`、`accepting_l4`，顺序不需要重做。需要补的是侧面合法性校验和 Reviewer 的明确审核要求。

## 2. 可以直接复用的现有能力

| Persona snapshot | 每个任务绑定不可变人格版本 | 直接承担 L0 版本冻结，不新增独立 L0 版本表 |

| DeliveryReport | 已包含侧面、理由和 L0 Gate | 保持 API 输出不变 |

## 3. 新增模块：`l0_policy.py`

所有新增 L0 能力集中到一个纯领域模块，避免散落在 Prompt、Worker、Repository 和 UI 中。

### 3.1 `parse_l0(text)`

职责：

- 从 `l0.md` 提取母题、变体、雷区和温度。
- 支持两种输入：
  - 当前 persona 使用的带归属/状态列表。
  - 领导原文使用的 Markdown 表格和自然段。
- 返回不可变的 `L0Policy`。
- 缺少母题、可用变体、雷区或温度时拒绝加载。

这样领导原文可以原样进入 persona 的 `l0.md`，无需先改写成另一份运行文档。

### 3.2 `validate_selection(policy, selected_l0_variant)`

职责：

- 验证模型返回值属于当前 `policy.variants`。
- 对有显式 ID 的 L0，只接受 A/B/C/D 等 ID。
- 对现有旧 persona，继续接受其原有的准确变体文本，避免一次性迁移四个现有 persona。
- 返回规范化后的选择值；非法选择抛出安全的协议错误。

第一版继续使用现有 `selected_l0_variant: str`，不修改 Pydantic schema 和 API。

### 3.3 `validate_gate_evidence(evidence)`

职责：检查现有 Quality Reviewer 的 `evidence` 是否明确包含：

1. `母题兑现`：哪些关键集和场真正回答了选定侧面。
2. `雷区`：是否依靠旁白、心理解释或端腔抒情说破母题。
3. `温度`：暖、灾、峰值、收拍和留白是否成立。

该函数只校验证据结构，不替 Reviewer 判断作品质量。`passed` 为真但缺少任一部分时，Worker 不批准该 Gate。

### 3.4 `summarize_variant_usage(records)`

职责：从现有 checkpoint 或交付记录中汇总：

- A/B/C/D 各自使用次数。
- 各 L0 snapshot 的使用次数。
- L0 Gate 通过和拒绝次数。

第一版只提供纯汇总能力，数据继续来自现有持久化记录，不增加数据库表和前端页面。需要查看时生成只读报告；确认存在长期运营需求后，再决定是否增加 Repository 查询或管理界面。

### 3.5 `diff_l0(old_text, new_text)`

职责：领导更新 L0 时，比较新旧文档，输出变化类别：

- 母题变化。
- 变体新增、删除或修改。
- 雷区变化。
- 温度变化。
- 使用顺序变化。

该函数只生成升级影响报告，不自动修改代码、不自动创建 persona 版本、不自动上线。

## 4. 三个最小接入点

### 4.1 `personas.py`：装载时解析一次

最小改动：

1. 用 `parse_l0()` 替代当前只识别列表标记的 `_validate_l0_markers()`。
2. 在 `PersonaCatalog` 中按 snapshot hash 缓存 `L0Policy`。
3. 提供 `load_l0_policy(snapshot_sha256)` 给 Worker 使用。

保持不变：

- persona manifest。
- 九文件数量和路径。
- snapshot hash 规则。
- `/persona/l0.md` 注入方式。
- L1–L6 处理逻辑。

### 4.2 `worker.py`：checkpoint 前校验一次

现有 `approve_stage()` 是最小接入点。

当阶段为 `SELECTING_L0_VARIANT` 时：

1. 从 `PersonaCatalog` 取得当前 snapshot 的 `L0Policy`。
2. 调用 `validate_selection()`。
3. 非法值不写 checkpoint，按现有结构化输出失败机制处理。
4. 合法值按原有 payload 写入 durable checkpoint。

当阶段为 `ACCEPTING_L0` 且 `passed=true` 时：

1. 调用 `validate_gate_evidence()`。
2. evidence 缺少“母题兑现、雷区、温度”任一部分时不批准 checkpoint。
3. evidence 完整时继续使用现有 Gate 和 checkpoint 流程。

Checkpoint 已经和当前 run、persona snapshot 绑定，所以不新增数据库表，也不重新设计恢复流程。

### 4.3 `agents.py`：收紧两个提示

最小改动：

1. Story Architect 在选择阶段必须从 `/persona/l0.md` 返回准确 ID 或准确变体值，不得重命名。
2. Quality Reviewer 在 `accepting_l0` 阶段按“母题兑现、雷区、温度”三段写 evidence；具体内容仍从 `/persona/l0.md` 和已批准作品中读取。

保持不变：

- Agent 数量。
- Supervisor 路由。
- 五个创作阶段。
- `StoryArchitectResult`。
- `QualityReviewerResult`。
- L0/L4 Gate 顺序。

## 5. 第一版不需要改动的模块

| 模块 | 不改原因 |
| --- | --- |
| `schemas.py` | 现有字符串选择和 `passed + evidence` 足以承载第一版；在应用层加强校验即可 |
| `repository.py` | 选择、理由、snapshot 和 Gate 已经持久化；第一版可以直接从 checkpoint/交付数据汇总 |
| `observability.py` | 先复用现有 stage 和 Gate 事件；有实际运营需求后再增加分布指标 |
| `contracts/persona-package.schema.json` | 九文件协议不变，L0 内部结构由领域解析器负责 |
| API/frontend | 对外数据结构和用户流程不变 |
| `series_bible.py` / `continuity.py` | 它们负责故事事实连续性，不承担人格母题规则 |
| `skill_assets.py` | L0 是强制人格规则，不是按需 Skill |

- 能解析领导原文的表格格式。
- 能解析现有 persona 的列表格式。
- 准确提取母题、变体、雷区和温度。
- 缺字段时失败。
- A/B/C/D 合法，新侧面非法。

现有测试只做少量补充：

- `tests/test_worker.py`：非法侧面不能写 checkpoint，合法侧面沿用现有流程。
- `tests/test_agents.py`：选择提示不允许重命名；L0 Gate evidence 包含母题、雷区、温度三段。

真实模型验收继续复用现有 `tests/live/test_real_model_e2e.py`，使用隔离 persona 和数据库验证一次合法选择、一次非法选择拒绝和一次 L0 Gate。

## 7. 领导更新文档时的升级方式

由用户明确触发：提供或指定更新后的 L0，并要求重新分析。

```text
读取新原文
  -> diff_l0(old, new)
  -> 输出变化和影响模块
  -> 人工确认升级范围
  -> 必要时修改 l0_policy.py、Prompt 和测试
  -> 更新 persona/l0.md 及 manifest hash
  -> 生成新 persona snapshot
  -> 隔离真实模型验收
  -> 新任务使用新版本
```

变化与最小升级范围：

| 原文变化 | 最小系统升级 |
| --- | --- |
| 只改措辞，结构和语义不变 | 更新 `l0.md`、manifest hash 和回归快照；模块无需改动 |
| 修改 A/B/C/D | 更新解析结果、选择测试和 Agent 对照用例 |
| 修改雷区或温度 | 更新 `review_instruction()` 及 Reviewer 回归用例 |
| 增加新的机器读法 | 先判断是否应扩展 `L0Policy`；确有必要才增加字段和接入点 |
| 修改使用顺序 | 才考虑改 Worker/Workflow；不提前预留复杂状态 |

历史任务不迁移、不覆盖，继续使用创建时的 persona snapshot。

## 8. 实施顺序

1. 新增 `l0_policy.py` 和单元测试。
2. 在 `personas.py` 接入解析和缓存。
3. 在 `worker.py` 增加选择值校验。
4. 在 `agents.py` 收紧选择和审核提示。
5. 跑现有 persona、worker、agent 和集成测试，确认四个旧 persona 不受影响。
6. 用领导原文建立隔离 persona，执行真实模型验收。

完成标准：

- 原始 L0 指纹不变。
- 领导原文可以原样作为 `l0.md` 被装载。
- 四个现有 persona 无需迁移。
- A/B/C/D 之外的选择不能进入 checkpoint。
- 后续阶段继续使用现有 snapshot 和 checkpoint。
- L0 Gate 明确审核母题、雷区、温度。
- API、前端、数据库 schema 和工作流阶段无变化。

## 9. 本轮最终方案

当前 L0 只增加一个独立能力模块，并在三个位置薄接入：

```text
l0_policy.py（新增核心能力）
  -> personas.py（解析与缓存）
  -> worker.py（选择校验）
  -> agents.py（生成与审核约束）
```

其余系统尽量复用。未来文档更新时，优先扩展这个模块；只有新原文确实改变工作流、权限、存储或对外合同，才修改对应模块。
