# Pengine L0 接入设计

> 状态：讨论稿，不代表已经实施。

>
> 原始来源：[L0内核母题.md](../L0内核母题.md)

## 决策摘要

领导提供的 L0 应作为**只读权威来源**保留，不为适配 Pengine 而改写。Pengine 通过一个可追溯的编译过程，从原始 L0 生成运行时投影、结构化约束和任务状态；所有派生内容必须能反向定位到原文，不能产生原文没有的新母题、新侧面或新判断权。

推荐的接入形态不是“把整篇 L0 塞进 Prompt”，也不是“把 L0 存成 Memory”，而是：

```text
原始 L0（只读权威来源）
  -> 人工批准的 L0 编译
     -> 运行时 L0 上下文
     -> 变体枚举与权限策略
     -> 雷区与温度规则
  -> 每单选择一个 L0 侧面
  -> 五阶段创作始终携带该选择
  -> 独立 L0 总闸
  -> 任务留痕与跨任务分布统计
```

L0 不是长期记忆。L0 是人格资产；选中的侧面和理由是任务状态；跨任务侧面使用情况是统计数据。用户反馈和模型输出都不得反向修改 L0。

# 01 架构决策

## 1.1 场景与目标

| 项目 | 判断 |
| --- | --- |
| 业务目标 | 让每一单短剧都经过领导定义的 L0 轴心，而不是只使用通用短剧技巧 |
| 当前系统形态 | 固定阶段工作流 + 专业 Agent + 独立 Reviewer + 不可变 persona 快照 |
| Agent 适配度 | `strong_fit`：情境到母题侧面的翻译需要语义判断，但流程和权限必须由系统控制 |
| 推荐方案类型 | `workflow_agent_hybrid + reviewer` |
| 技术风险 | 中：错误接入会造成无效提示、选择越界或审核形同虚设 |
| 治理风险 | 高：L0 属于真实创作者，涉及人格解释权、修改权和作品归属 |
| 自治等级 | 受监督自治：Agent 可以选择侧面，不能创建、修改或删除侧面 |

成功不是“模型看过 L0”，而是以下事实都能被验证：

1. 当前任务使用了哪个 L0 版本。
2. 选择的是 A/B/C/D 中哪个侧面，为什么。
3. 后续所有阶段都读取同一个已冻结选择。
4. L0 总闸能引用成片中的具体证据，而不是只返回“符合”。
5. 任务、用户反馈和模型均不能修改 L0。
6. 运营者能查看侧面分布，但系统不能自行调平或反写人格资产。

## 1.2 候选方案比较

| 方案 | 优点 | 根本问题 | 结论 |
| --- | --- | --- | --- |
| 原文整体放进系统 Prompt | 实现快，原文完整 | 规则不可结构化验证；选定侧面、权限、统计仍靠模型自觉 | 不采用 |
| 把 L0 存成长期 Memory | 可以跨任务召回 | Memory 会被更新、合并或遗忘，违背 L0 只读与版本权威性 | 禁止 |
| 把 L0 做成一个 Skill | 可以写步骤和输出要求 | Skill 适合“怎么做”，不适合作为创作者最高人格资产和数据源 | 不作为主载体 |
| 把 L0 做成 RAG | 可按需检索，节省上下文 | L0 每单必须生效，不能依赖模型是否想起来检索 | 不作为主载体 |
| 仅把规则写死在代码中 | 可强约束 | 会丢失创作者原话、语义和版本来源，规则变更也难以由内容侧维护 | 不采用 |
| 原文只读 + 编译投影 + 工作流状态 + Reviewer | 保留权威来源，同时实现枚举、权限、留痕、审核和统计 | 需要增加编译与验证能力 | 推荐 |

## 1.3 推荐架构

主控制模式为 `hybrid_controlled`：

- Workflow 控制装载、冻结、阶段顺序、状态传递、总闸和留痕。
- Agent 只负责把用户故事翻译到已有 L0 侧面，并生成创作内容。
- Reviewer 独立判断成品是否兑现选定侧面、是否触碰雷区、是否符合温度。
- Human Approval 控制 L0 来源版本和编译结果的发布。
- Observability 记录选择分布和失败原因，不自动改变选择策略。

不引入新的自由 ReAct 流程，不因 L0 单独增加多 Agent。现有专业 Agent 与独立 Reviewer 已足够承载这一职责。

## 1.4 允许与禁止的自治范围

### Agent 可以做

- 阅读当前快照对应的 L0 运行投影。
- 在批准的 A/B/C/D 中选择一个侧面。
- 给出与用户故事对应的选择理由。
- 在创作阶段执行已经冻结的侧面、雷区和温度约束。
- 在审核阶段引用作品中的具体证据。

### Agent 不可以做

- 发明 E 或任何新侧面。
- 改写 A/B/C/D 的含义。
- 因为用户偏好、平台趋势或历史分布修改 L0。
- 用 L1–L6、用户需求或外部技法覆盖 L0。
- 把本单反馈沉淀为 L0 更新。
- 以“分布均衡”为理由选择语义不匹配的侧面。

## 2.1 原文条款到系统载体的映射

| --- | --- | --- | --- | --- |
| 第 7–15 行：母题 | L0 唯一轴心 | 运行时 L0 常驻上下文 | 所有阶段的最高语义目标 | 仅源本人发起 |

| 第 29–42 行：A/B/C/D 变体 | 受控选择空间 | 结构化变体枚举 | 翻译阶段只能选已有侧面 | 仅随批准的新 L0 版本更新 |
| 第 44–48 行：反面雷区 | 质量红线 | 语义 Reviewer + 谨慎的确定性检查 | 各阶段检查；最终总闸复核 | 仅随批准版本更新 |
| 第 50–54 行：温度 | 风格与情绪纪律 | 生成约束 + Reviewer rubric + 可计算约束 | 约束全片气质和单集峰值 | 仅随批准版本更新 |

| 第 78–87 行：归属与状态 | 治理元数据 | ownership/status/version metadata | 展示权威、状态和修改权限 | 仅批准流程 |

这里的“编译”只改变数据形态，不改变语义。例如表格中的侧面可以被编译成枚举，但系统不能重新命名、合并或改写其定义。

## 2.3 各类能力边界

### Agent

负责动态语义判断：用户故事更符合哪个既有侧面，以及作品如何落实该侧面。Agent 不拥有 L0 数据结构和修改权。

### Workflow

负责不可绕过的固定链路：装载 L0、选择侧面、校验枚举、冻结绑定、按阶段传递、执行总闸、保存结果。即使模型忽略提示，Workflow 也必须阻止越界选择和跳过总闸。

### Tool

L0 第一阶段不需要开放写工具。后续如增加编译或审批工具，其权限必须限定为：读取已批准来源、生成派生投影、提交待批准版本；不能直接覆盖原始文件或激活版本。

### RAG

L0 不采用按需 RAG。它是每单必需的核心上下文，不应依赖模型决定是否检索。L5/L6 后续可以使用 RAG，但检索结果必须服从本单已冻结的 L0。

### Memory

L0 不进入 Memory。Memory 不得创建、覆盖、补全或调权 L0。侧面选择是任务状态，侧面分布是统计，二者均不属于人格记忆。

### Human

源本人或明确授权者拥有 L0 的最终解释权、修改发起权和版本批准权。系统可以生成差异和风险提示，但不能替人批准。

# 03 控制流、数据流与状态

## 3.1 来源编译流

```text
[原始 L0 文件]
  -> 计算来源指纹
  -> 检查文件是否为已批准版本
  -> 确定性抽取母题、A/B/C/D、雷区、温度、归属和状态
  -> 结构与来源一致性验证
  -> 人工查看原文到派生物的差异
  -> 批准
  -> 生成内容寻址的 persona 快照和编译缓存
```

任何一步失败，都不得用旧规则加新文本“凑一个可运行版本”。系统应拒绝发布，并保留当前已批准版本。

## 3.2 单任务控制流

```text
用户故事与需求
  -> 装载已批准的 persona snapshot
  -> Workflow 提供母题与 A/B/C/D
  -> L0 Translator Agent 选择一个侧面并给出理由
  -> Policy Guard 校验 variant_id 属于当前版本
     -> 不属于：拒绝并要求重选
     -> 属于：冻结 Task L0 Binding
  -> 五阶段创作始终读取同一绑定
  -> L0 Reviewer 审核母题兑现、雷区和温度
     -> 不通过：进入受限重试或任务失败
     -> 通过：保存 Gate 证据并交给 L4 闸
  -> 完整交付
  -> 生成侧面台账记录和统计投影
```

## 3.3 数据流

```text
原始 L0
  -> canonical source hash
  -> compiled L0 version
  -> persona snapshot hash
  -> task L0 binding
  -> stage checkpoints / SeriesBible lineage
  -> delivery report / L0 gate evidence
  -> variant ledger
  -> aggregate analytics
```

数据只允许向右流动。任务绑定、审核结果、用户反馈、侧面台账和统计均不得倒灌到编译结果或原始 L0。

## 3.4 任务状态

| 状态 | 触发 | 下一状态 | Owner |
| --- | --- | --- | --- |
| `l0_source_loaded` | persona 快照装载成功 | `l0_selection_pending` | Workflow |
| `l0_selection_pending` | Agent 返回选择 | `l0_selection_validating` | Agent |
| `l0_selection_validating` | 枚举、版本、格式校验 | `l0_bound` 或重试/失败 | Policy Guard |
| `l0_bound` | 选择冻结并持久化 | 五阶段创作 | Workflow |
| `l0_review_pending` | 五阶段完成 | `l0_reviewing` | Workflow |
| `l0_reviewing` | Reviewer 返回结构化证据 | `l0_passed` 或拒绝 | Reviewer + Workflow |
| `l0_passed` | Gate 记录持久化 | L4 Gate | Workflow |
| `delivered` | 所有闸通过 | 台账和统计投影 | Repository/Observability |

## 3.5 Human Approval 流

```text
源本人发起 L0 变更
  -> 新来源版本，不覆盖旧文件对应的已批准记录
  -> 系统展示原文 diff、派生 diff、受影响规则
  -> 授权者确认来源、语义和生效时间
  -> 发布新版本
  -> 新任务使用新快照
  -> 历史任务继续绑定旧快照，可完整回放
```

运营者、用户和模型均不能发起“自动生效”的 L0 修改。若实际业务决定允许代理人提交变更，也只能提交候选版本，最终批准权仍需明确记录。

## 3.6 错误处理

| 错误 | 处理 |
| --- | --- |
| 来源指纹与批准记录不一致 | 拒绝装载，报告来源版本异常 |
| 原文缺少必要结构 | 拒绝编译，不能由模型猜测缺失项 |
| 派生投影无法追溯到原文 | 拒绝发布 |
| Agent 返回不存在的侧面 | 不进入后续阶段，有限重试后失败 |
| 后续阶段使用了不同侧面 | 视为状态/协议错误，不能自动改绑 |
| L0 Reviewer 没有具体作品证据 | Gate 无效，要求重新审核 |
| 雷区确定性检查与语义审核冲突 | 不自动放行或定罪，记录冲突并由受控 Reviewer 重新判断 |
| 侧面分布长期失衡 | 只生成运营提示，由真人判断；系统不自动改权重 |

# 04 风险边界与护栏

## 4.1 风险边界

| 边界 | 要求 |
| --- | --- |
| Source | 原始 L0 不因技术适配被修改；必须保留指纹和历史版本 |
| Data | 任务数据与统计数据不能反向写入人格资产 |
| Agent | 只能选择既有侧面，不能重新解释选择空间 |
| Workflow | 任何路径都不能跳过 L0 选择、绑定和总闸 |
| Memory | L0、任务绑定和统计均不得混入可自更新长期 Memory |
| Output | Gate 必须给出成片证据；自我宣称不构成通过依据 |
| Human | L0 更新必须记录批准主体和生效时间 |
| Cost | L0 校验不应引入无上限重试；失败必须有终止状态 |

## 4.2 必需护栏

1. **内容寻址**：每个任务绑定确切 persona snapshot 和 L0 编译版本。
2. **枚举校验**：选择值必须属于当前批准版本，不能只检查非空。
3. **只读权限**：运行 Agent 对原始文件、persona snapshot 和编译缓存无写权限。
4. **方向约束**：来源可以生成台账枚举，台账不能生成或修改来源。
5. **独立审核**：生成 Agent 不能自行宣布 L0 Gate 通过。
6. **证据要求**：Reviewer 必须引用具体集、场、动作、台词或结构位置。
7. **语义优先**：雷区中的“文艺腔”“心理描写”等不能仅靠关键词粗暴定罪。
8. **审核可回放**：保存输入版本、输出指纹、Reviewer 结果和调用身份。
9. **人工发布**：L0 新版本只有批准后才能供新任务选择。
10. **统计不自治**：分布异常只提醒，不自动调权或强行均衡。

## 4.3 主要失败模式

### 原文被“规范化”成另一套人格

如果编译过程允许模型自由摘要，可能把领导的原话改成听起来更标准、但语义已经变化的版本。第一版编译必须是确定性抽取；任何人工编辑都要进入批准 diff。

### 侧面名称是枚举，侧面含义却漂移

只校验 `A/B/C/D` 不够。运行投影必须同时绑定该版本对应的完整定义；Reviewer 也必须按同一版本判断。

### 雷区检查误伤正常剧作

“旁白”“心理描写”“文艺腔”包含语境判断。关键词可以定位候选风险，但不能单独作为最终拒绝依据；台词和叙述也要区分。

### L0 Gate 成为形式化自述

如果只让模型回答“本片体现了初心与现实”，任何作品都能通过。必须要求可核验的剧情证据，并检查这些证据是否贯穿核心因果，而非只在台词中点题。

### 为了统计均衡牺牲语义匹配

侧面台账的作用是暴露重复倾向，不是把下一单轮流分配给低频侧面。校准权属于真人，系统不能把统计目标置于用户故事和 L0 语义之上。

## 4.4 当前不能确认的事项

本设计不能代替以下业务确认：

- 源本人的正式开线授权范围。
- 谁是系统中可记录的 L0 最终批准者。
- 署名、商业权益、抽检、叫停和下架的具体合同。
- 当前原始文件指纹是否已被正式批准为生产版本。

在这些事项确认前，可以进行隔离环境中的技术验证，但不能把该人格称为已获授权的生产人格。

# 05 实施顺序、验收与后续设计

## 5.1 建议实施顺序

### Phase 0：批准本接入设计

- 确认原始文件永不因技术适配被改写。
- 确认 L0 的数据分类和职责边界。
- 确认 A/B/C/D 是封闭枚举。
- 确认统计只用于人工观察。

### Phase 1：L0 编译与合同

- 定义原文到运行投影的确定性映射。
- 让运行投影满足 persona 包现有归属/状态要求。
- 建立来源指纹、版本和批准记录。
- 增加编译一致性测试。

### Phase 2：选择与冻结

- 为 A/B/C/D 建立稳定 `variant_id`。
- 在 Workflow 中校验选择属于当前版本。
- 冻结任务 L0 绑定并贯穿后续阶段。

### Phase 3：雷区、温度与 L0 Gate

- 把语义审核与可计算规则分开。
- 设计 L0 Reviewer 的证据合同。
- 防止生成者自审和 Gate 空泛通过。

### Phase 4：台账与观察

- 从已冻结任务绑定生成侧面台账。
- 提供分布和重复倾向观察。
- 不实现自动调平和自动反写。

### Phase 5：隔离真实模型验收

- 使用隔离 persona、数据库和新任务运行。
- 检查真实模型看到的 `/persona/l0.md` 和冻结绑定。
- 设计同一故事在不同合法侧面下的对照用例。
- 验证非法侧面、无证据 Gate、雷区误报和版本切换。

## 5.2 最低验收标准

| 验收项 | 通过条件 |
| --- | --- |
| 原文保护 | 实施前后原始 L0 指纹不变 |
| 编译追溯 | 每个派生字段都有原文位置和来源版本 |
| 选择封闭 | A/B/C/D 之外的结果不能进入下一阶段 |
| 状态冻结 | 后续五阶段和两道总闸使用同一个 L0 绑定 |
| 任务留痕 | 可查询侧面、理由、版本、时间和任务 ID |
| Gate 真实性 | Reviewer 给出具体成片证据；空泛自述不能通过 |
| 权限 | 用户反馈、模型和任务流均无法改写 L0 |
| 回放 | 历史任务能按当时的 L0 快照复现上下文 |
| 统计隔离 | 分布统计不会自动改变人格或下一单选择 |
| 真实调用 | 新建隔离任务证明真实提供方调用读取并执行了 L0，而非只通过单元测试 |

## 5.3 后续 Skill 路由

| 优先级 | 后续设计 | 需要的输入 |
| --- | --- | --- |
| P0 | Workflow 设计 | 本文批准版本、现有阶段状态机、重试与 Gate 合同 |
| P0 | 安全与权限设计 | L0 批准角色、来源目录、发布与回滚权限 |
| P1 | Tool/Compiler 设计 | 原文结构、运行投影合同、persona schema 变更选择 |
| P1 | Workflow Eval 设计 | A/B/C/D 对照案例、雷区边界案例、温度案例 |
| P2 | 可观测性设计 | 任务绑定、Gate、模型调用和分布指标 |
| 暂缓 | Memory 设计 | L0 不需要 Memory；待后续研究 L4/L6 资产级反馈时再启动 |

## 5.4 进入实现前必须决定的问题

1. 原始 L0 当前版本是否已经获得可用于技术验证的明确授权。
2. 运行投影是保留完整原文，还是“完整母题 + 结构化三面”；两者都必须由同一来源生成。
3. `variant_id` 使用 `A/B/C/D`，还是引入更稳定、不随展示名变化的内部 ID。
4. 结构化编译结果采用按 snapshot hash 的外部缓存，还是升级 persona manifest。
5. L0 Gate 的具体证据粒度：至少到集，还是必须到场。
6. 雷区确定性检查失败时，是直接拒绝，还是只交给语义 Reviewer 复核。
7. 谁能批准 L0 新版本，批准记录以什么形式进入系统。

## 最终边界

L0 接入完成后，系统应当更忠实、更可验证地执行领导的原始定义，而不是拥有解释或改造领导人格的权力。

原始 L0 是源；运行投影、选择结果、审核结果和统计都是它的派生物。派生物可以重建，源不能被派生物反向改写。
